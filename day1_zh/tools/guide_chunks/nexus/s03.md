## [11:00 AM] 工作坊：建立 Token 高效的 OpenClaw 代理型系統（由 AMD 提供）

**講者**

- Mahdi Ghodsi（AMD AI 解決方案架構師）
- Satya Devineni（AMD 產品應用工程師）
- Eda Zhou（AMD 軟體開發工程師）

### 預算是怎麼被燒光的

年初，AMD 幫一個團隊編列了全年的運算預算。結果呢，幾週內就用完了。Mahdi Ghodsi 在台上講這件事的時候，語氣不是抱怨，比較像是在描述一個已經在整個產業重演的現象：兩個使用者用同一個服務，一個人的成本可能是另一個人的十倍，甚至一百倍。差距不是來自誰用得比較兇，而是來自任務本身的性質——某一次呼叫可能只是問個問題，另一次卻觸發了一整輪代理迴圈，一路呼叫工具、檢查結果、不滿意再呼叫一次，甚至展開一整組代理協作。

這正是這場演講要處理的核心矛盾：舊的產能規劃邏輯，是用「席位」去分配使用者給模型，隱含的假設是每次互動的運算量大致相近。這個假設在一般聊天情境裡成立——使用者送出提示、拿到回應，任務有邊界，結束了。但代理型 AI 沒有邊界，同一件工作可能花幾秒，也可能花好幾個小時。用「席位」去規劃一個運算量可以相差百倍的系統，編列出來的預算當然守不住。

### 舊指標為什麼失靈

過去大家執著的是每秒能處理多少 token、GPU 夠不夠快。Mahdi 講得很直接：這個指標現在其實告訴不了你需要多少運算資源，因為重點從來不是單一次回應，而是「完成整個任務」要花多少代價。多輪代理執行讓上下文成長得飛快，系統很大一部分被記憶體頻寬卡住，而不是算力本身。衡量單位如果還停留在「每秒吐幾個字」，就等於用錯的尺量錯的東西。

他們提出的替代原則其實很樸素：每一輪對話都在重複上一輪已經做過的工作，那為什麼不把算過的結果留下來，而要重新算一次？這個想法本身不新，新的是做法——同時在三個層面做快取：模型層、GPU 服務堆疊層、CPU 層。

模型層的例子是 Kimi K3：93 層裡有 69 層換成了 KDA（Kimi Delta Attention），一種帶循環層的線性注意力機制，這些層需要計算的 token 數量是固定的。AMD 用 MI355 GPU 測試，一個節點八張卡、每張 288GB，結果只用了大約 15.5GB 記憶體。GPU 堆疊層的做法，是把原本只有 HBM 一層的快取，重新設計成 HBM、CPU 的 DRAM、SSD、共享記憶體池的分層架構，讓代理在等工具呼叫回來的閒置時間裡，前綴資料早就準備好、隨時可以用。這一項改動把第 99 百分位延遲從 17.3 秒壓到 5.4 秒，快了 3.2 倍。CPU 層則是把分詞（tokenization）結果也快取起來，只算新增的部分，穩定落在 0.09 毫秒，相較整個重算要花 1.7 秒。

### 一個會讓人算錯方向的細節

這裡有個值得停下來的地方。同一組實驗裡，快取命中率其實是下降的——從 88.5% 掉到 87.5%。單看這個數字，會覺得系統變差了。但真正被優化的是首個 token 出現的時間，而使用者體驗是靠這個撐起來的，不是靠命中率。Mahdi 的結論很明確：命中率再高，如果算出第一個 token 要等很久，那個數字沒有意義。這也是這場演講真正想立的方法論主張——衡量單位要換成「每次成功完成執行的成本與時間」，不是每秒 token 數，也不是快取命中率這類看起來像效能指標、實際上跟使用者體驗脫鉤的中間變數。贏家是用最少成本完成最多任務的人，不是快取打得最漂亮的人。

這個主張的邊界也在這裡浮現：它成立的前提，是任務本身有「多輪、可重複利用前文」這個結構。一次性的、無需上下文累積的呼叫，快取分層帶來的節省有限，衡量單位換不換其實差別不大。這套方法是為代理迴圈這種特定形狀的負載設計的，不是放諸四海皆準的效能公式。

### 從快取到路由：另一種省 token 的方式

簡報結束後轉入工作坊，主題換了一個角度：不是靠快取重複計算，而是靠決定「這個任務根本不需要送到最貴的模型」。Mahdi 把這個想法接到一個老概念上——1991 年 Hinton 團隊就談過路由，2017 年在超過一兆參數的模型上重新驗證，發展出稀疏門控（sparse gating），這條路線一路走到今天的 MOE。差別在於，這個工作坊把路由的對象從「模型內部的專家」換成「整個模型」：本地端一台 AMD Ryzen AI Halo 主機（128GB 統一記憶體，低精度下可以跑到兩千億參數等級的模型），搭配雲端的 Kimi 模型，由代理自己判斷該送去哪裡。

這個做法不是 AMD 自己發明的。2023 年的 FrugalGPT 用一個模型判斷小模型的回應夠不夠好，不夠好才升級雲端，宣稱能省下高達 99% 的成本、品質接近當時的 GPT-4；柏克萊後續的研究改成用獨立路由器直接決定該用哪個模型，也顯示能省下兩倍以上的成本。工作坊示範的四種路由方式，從最原始的手動切換模型，到專屬代理搭配權限規則，到 SOUL.md 裡寫規則自動升級，最後是 Lemonade 用嵌入向量與餘弦相似度做語意路由——複雜度依序疊加，但共同的判斷邏輯只有一個：這個 token 值不值得送到最貴的模型。

支撐這個判斷的有三根柱子：成本（找檔案、跑簡單指令不需要前沿模型）、品質（需要時再升級，或用專門模型處理專門任務）、隱私與安全（個人檔案留在本機，社會安全碼不該出現在別人的訓練資料裡）。HR、福利、財務三個示範代理，也確實是照這三根柱子在切——包含個資的到職流程整段留在本地模型處理，簡單的福利指標查詢交給本地，涉及比較分析或字數超過門檻的複雜查詢才升級雲端。

這裡同樣有邊界要說清楚。語意路由靠的是關鍵字、正規表示式、嵌入相似度門檻（0.6、0.72、0.5 這類人工設定的數字）跟一個小模型做分類，判斷本身會出錯，門檻也需要為每個場景手動調整——HR、福利、財務這三個示範能跑得順，是因為任務類型本來就相對固定、邊界清楚。換成開放式、難以歸類的任務，路由規則能不能一樣可靠，這場演講並沒有給答案，也沒有打算給。

Mahdi 最後把整場定調成一句話：不需要的運算就不要算。這句話同時是快取的理由，也是路由的理由——只是前者省的是重複計算，後者省的是不必要的模型等級。兩者合起來，才是這場工作坊真正想教的「token 效率」，而不是單一個工具或單一個技巧。
