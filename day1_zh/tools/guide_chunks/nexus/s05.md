## [01:30 PM] 第 2 場：編碼與網頁代理人 — 精選演講

**講者**

- Silas Alberti（Cognition 研究資深副總裁） —— 擴展編碼代理人的強化學習 (RL) - 訓練 SWE-1.7 的經驗教訓
- Dhruv Batra（Yutori 首席科學家兼共同創辦人） —— 電腦使用模型將使網頁代理人化，而非 API
- Shamir Abdul Aziz（微軟首席產品經理） —— 零營運 (Zero Ops) - 代理人操作，人類治理
- Krishnakumar Sharma（Omokai 執行長） —— 代理型編碼，以無聊的方式

這幾年業界對「代理人怎麼跟世界介接」有個幾乎沒人質疑的默契：靠 API。MCP、web MCP、支付協定，一種一種標準疊上去，彷彿只要接口鋪得夠密，代理人自然就能操作一切。這場的第二位講者 Dhruv Batra，當場拿一個電商網站戳破了這個默契。他要查一顆二十四毫米的鋨方塊有沒有現貨，畫面上的數量下拉選單清清楚楚顯示三個品項灰掉、一個可選——人一眼就看得出來。但代理人去讀這個頁面的 HTML，選單裡只有品項描述，完全沒有數量。真正的庫存數字，是頁面載入時另外抓的一個 JSON，跟畫面顯示邏輯是兩段互不相通的程式碼。網路是為了人的眼睛蓋的，API 這個「援兵」，在他看來根本不會來。

四位講者剛好把這個裂縫從四個方向撐開——訓練端、介面端、企業治理端、工程紀律端各站一角，答案卻彼此頂撞。

### 連最友善的環境，都得靠蠻力才能撐起 API 式的代理人

如果有一種場景最接近「代理人靠結構化介面工作」的理想狀態，大概就是 Cognition 的編碼代理人：終端機、檔案系統、版本控制，全部都是乾淨的結構化工具呼叫，沒有像素、沒有 JavaScript 陷阱。Silas Alberti 講的是他們過去一年怎麼把這個「最簡單的情況」一路擴大。起點是三十二張 H200，用強化學習訓練模型寫 CUDA 核心，意外發現多輪訓練贏過單輪，還在 KernelBench 上打贏了 o3。接著是 SweGrep，一個只做「找出跟問題相關的檔案」的代理人，靠 F1 分數當獎勵，訓練出的模型能一次平行發出八個工具呼叫，靠 Cerebras 晶片跑到每秒三千個 token。

聽起來一路順風，但真正有意思的是代價。訓練到 SWE-1.6、SWE-1.7 這種要打真實編碼基準的模型時，團隊撞上熵崩潰——模型的思維鏈會逐漸失去多樣性，分數就此見頂。他們甚至發現一個怪異的早期警訊：這個模型的思考過程習慣以「okay」開頭，訓練後期，同樣一句開場白會從「好，各位，我需要最佳化這個三維張量矩陣乘法」滑向「好，我的天啊，我得把這段程式碼弄好」——語氣越來越絕望的那一刻，往往就是訓練即將發散的前兆。而為了把算力擴大到能跨澳洲、馬來西亞、加拿大、美國四國訓練，他們得靠非同步 RL，容忍訓練策略與推論策略之間的落差，這件事本身又反過來要求演算法先變穩定，才敢把這個落差的上限往上推。也就是說，即使是業界公認最乾淨、最容易寫成 API 呼叫的任務，把它訓練到前沿水準也遠不是「多加算力」這麼簡單。連這個最友善的起點都這麼難走，Dhruv 接下來要說的、關於整個開放網路的主張，才顯得更有份量。

### 那道不會來的援兵

Dhruv Batra 一上台就把矛頭指向一個具體的三段論：代理人會成為網路上行動的主角，這是對的；網路會因此被「代理人化」，這也對；但做法是靠 API，這一步他認為是錯的。他舉的第一個例子刻意挑得很好笑——用電腦操作代理人去點 flights.google.com 訂機票，明明有現成的聚合查詢服務可以直接呼叫，何必模擬人類點按鈕。但他馬上把問題推廣：如果你想知道一間餐廳菜單上有沒有無麩質品項，網站可能只是純文字，也可能是一份 PDF，最糟的情況是一整排掃描圖片拼起來、連 OCR 都沒做。光是歐洲某一個國家，就有大約二十萬個自己維護網站的小商家，這條長尾的價值加總起來很可觀，但基礎設施升級的速度慢得多。他的結論很直接：這些網站不會被重新打造成 API 閘道，我們等的援兵不會出現。

真正讓這個論點立住的，是他自己拆穿的另一條退路——「那就讓代理人直接讀程式碼」。他用那顆鋨方塊的例子說明，瀏覽器本質上是個渲染引擎，畫面呈現的邏輯和底層資料常常是兩套系統，讀 HTML 讀不到真正決定畫面的東西。所以他的主張是反過來的：機器必須靠視覺操作，網路才會被代理人化，而且是長尾那一段被代理人化，不是靠 API。他們做的 Navigator，輸入是瀏覽器截圖，輸出是點擊、輸入、捲動這類動作，可以拿去跑一遍模擬結帳流程，測試一組優惠碼有沒有讓價格下降百分之二十二。但他也強調，機器不必被綁在「像人一樣點按鈕」上，Navigator 有時候會直接寫 JavaScript，一次填完整張表單。至於「電腦使用模型是不是又慢又貴又停滯」這個常見質疑，他也用數字擋了回去：俄亥俄州立大學維護的一個基準測試，大約一個月前準確率已經衝到百分之九十七，基本上算打完了；在成本上，GPT-5.5 這類前沿模型跑一個動作要十秒、整個任務要花二點三美元，而他們訓練的專用模型準確度相當、速度更快。

### 微軟不選邊，把賭注放在治理而非介面

Shamir Abdul Aziz 的五分鐘演講，其實沒有選邊站在「API 還是像素」這個問題上——微軟關心的是另一件事：代理人已經有能力操作真實系統，問題是企業敢不敢放手。他把過去兩年在微軟的心得濃縮成一句話：模型是可以替換的，你可以隨時換一個更好的模型，但上下文、治理和工具不能替換，資源該投在這裡。他描述的「零營運」不是把人從營運裡拿掉，而是把營運這件苦差事從人身上拿掉，路徑要經過爬、走、跑、飛幾個階段——「飛」不是代理人做完就結束，而是它自己驗證結果，再把結果交給人確認。他舉的例子是一個修復 API 效能迴歸的代理人：光是建好 PR 還不夠，好的做法是把 PR 部署到測試環境、驗證迴歸確實消失，人類審查的是結果，不是逐行看 diff。

這段話回應了 Dhruv 那個沒說出口的問題：如果介面已經不是障礙，企業願不願意信任代理人去操作正式系統？微軟的答案是要有稽核、控制、評估、有信心的回滾，還要有證據證明代理人做的是對的事，少了這些，企業就是不會用。這也是為什麼他們要建權限機制，用可驗證的指標取代單純的信任。到目前為止，微軟企業層級已經部署超過五千個代理人，處理了一百五十萬件事故，其中將近二十二萬件已經自動化——這幾個數字撐住了他的論點：介面之爭之外，真正決定代理人能不能大規模落地的，是治理能不能同步跟上。

### 在既有系統裡，無聊才是最貴的能力

如果說前三位講者的分歧點在「代理人怎麼碰到系統」，Krishnakumar Sharma 直接把鏡頭拉遠，質疑「碰得到之後然後呢」。他先給了一個不留情面的判斷：我們正處在一種代理型宿醉裡——根據 Gartner 的研究，用更多 AI 不會帶來更高的生產力，只會讓 Anthropic 和 OpenAI 更有錢。他一條條點名現在流行的做法：上百個代理人組成的「代理人蜂群」，成本高、錯誤也多；迴圈裡面套迴圈的「迴圈工程」，同樣比預期貴得多。他也引用另一項研究，說不受控使用 AI 寫程式，最後會在正式環境的資料庫裡留下更多、更難清的錯誤，加上驗證、資安漏洞、除錯這些隱藏成本，還有他所謂的「AI 過勞」——過度依賴 AI 之後，人反而失去了對系統的掌握。

他的解法沒有花招，是他在 Amazon 學到的老辦法：框架與機制。二〇二五年他們做出的「D3 框架」，把代理型編碼拆成探索、計畫、交付三個階段——先產出一份涵蓋上下游相依關係的研究文件，再據此制定列出子任務的計畫，最後才讓 AI 去交付。他特別強調，這個階段還不能完全信任 AI，所以要有人工簽核；而且要用不同公司的模型交叉解決同一個問題，代理人數量控制在四個左右、定義清楚就好，不要貪多。他留給大家的最後一句話，是停止拚 token 用量，開始拚投資報酬率。

四個人其實是在同一個問題上，把賭注押在不同地方：Silas 賭的是即使介面已經最乾淨，訓練本身仍需要蠻力才能撐起前沿表現；Dhruv 賭介面本身——網路的長尾不會迎合 API，只能靠視覺；Shamir 賭治理——介面問題解決之後，信任才是真正的瓶頸；Krishna 則賭紀律，不管接的是 API 還是像素，沒有框架約束，代理人在既有系統裡照樣會闖禍。這場沒有人接話反駁誰，但把四段演講擺在一起看，答案已經很清楚不是一句「用 API 就好」能打發的。
