Miles 的重點在於，它是一套可以在大規模下穩定、有效率、而且結果可重現（reproducible）的強化學習系統，讓你可以用各式各樣的環境和獎勵設計，把強化學習任務跑在現代語言模型上，同時把所需的心力降到最低。整體來說，Miles 分成三層。第一層是 SGLang，做為 rollout 引擎，專門針對高吞吐量、多輪（multi-turn）生成做最佳化，而且跟現在的 agentic 系統、agentic 環境相容性也很好。中間這層是協調層（orchestration layer），把 rollout 引擎和後端訓練系統整合成一個整體，讓整個強化學習系統可以跑得很有效率。

最後，我們有各種不同的訓練引擎，例如 NVIDIA Megatron 和 FSDP，所以彈性也很高，你可以在自己的運算資源上客製化自己的訓練引擎。這張圖是 Miles 架構的重點示意圖。左邊是 rollout 引擎，透過跟外部環境或 agent 框架互動來產生軌跡（trajectory）資料，SGLang 負責這個生成層的最佳化，而環境本身可以依照客戶需求高度客製化或自動化。中間這部分，系統會把軌跡資料轉換成獎勵（reward）、損失函數（loss function）等等，變成訓練訊號。最後，如同前面提到的，我們有 Megatron 或 FSDP 的訓練後端，可以做前向、反向傳播，計算損失並更新模型權重。

最後，這些更新後的模型權重會同步回推論引擎，也就是 rollout 引擎，讓整個流程可以循環運作。那為什麼我們選 SGLang 當作 rollout 的後端呢？有幾個優點。第一，它跟強化學習的工作負載是共同演進（co-evolved）的，包含支援部分 rollout（partial rollout），也可以做到專屬的 rollout 控制，讓你可以很容易地指定自己的工作負載。第二，它的 rollout 設計效能非常高，例如有設計良好的快取感知（cache-aware）負載平衡，適合高吞吐量的生成；而且原生支援與訓練引擎的非同步生成，這在現今的強化學習演算法裡是非常重要的功能。

這裡有一些系統設計上更技術性的細節。首先是 rollout 引擎，我們支援多輪（multi-turn），這個前面已經提過很多次了。具體來說，我們支援 token-in、token-out（簡稱 TITO），也就是說，同一個多輪生成過程不需要一直重複做 tokenize 和 detokenize，這樣可以省下很多成本，也讓訓練更穩定。我們還有針對 MoE 模型的 R3（route replay，路由重放），意思是說，在用強化學習訓練 MoE 模型時，你不用擔心重放（replay）的問題──也就是說，不同次執行時，同一個請求可能會被路由到不同的專家（expert），我們不希望這樣，所以用 R3 來確保結果完全可重現。

但即便如此還是不夠。你可以看到 Sam（Altman）常常在推特上發文說，欸，我們還需要更多更多 GPU，如果有誰能幫我們弄到更多 GPU 儘管打電話給我們。所以，如果目前全世界市值最高的公司都沒辦法拿到足夠的 GPU，如果他們都沒辦法把資源集中在單一叢集裡，那你大概也很難做到。這波 GPU 荒是真真切切在發生的。如果你看看現在典型的 AI 組織，通常會有一個 AI 團隊，手上握有一些 NeoCloud（新興雲端業者）的保留額度，可能是在超大規模雲端業者（hyperscaler）產能不足的時候，跟其中一家 NeoCloud 簽了兩年或三年的合約。接著他們又加了一些隨需（on-demand）的執行個體，可能是跟 hyperscaler 租的，用來補足產能。

但接著他們往往還會有一些地端（on-prem）叢集，可能是出於法規因素，或者他們就是想把資料留在自己機房。接著又有歐洲的客戶，所以你還得在歐洲也架一套叢集，等於還要再維護另一套叢集。最後，你還需要大量的 CPU 來跑各種環境和沙箱（sandbox），為此又得維護另一套 CPU 叢集。所以每一項都是在當下那個時間點看起來合理的決定，但累積下來，你手上就有一大堆叢集要負責管理。而在某種程度上，強化學習讓這件事變得更糟，因為它把整件事變成一個排程（scheduling）問題。如果你想想現在的強化學習，整件事看起來是一個工作（job），但其實是由很多個子元件組成的。

舉例來說，訓練端本身需要大量的 VRAM，需要很多顆很強的 GPU；但同時，rollout server（實際負責產生軌跡資料的那一端）不需要那麼多 VRAM，但需要非常多顆，才能同時產生大量的軌跡資料。最後，如果要真的執行任務，比如說你在做程式碼生成模型，你的沙箱就需要大量的 CPU 平行運作，把所有軌跡都跑過一遍，而且沙箱上也需要非常快的程式碼環境。所以問題來了：為什麼不直接用現有的解決方案呢？像叢集管理這件事我們已經做了很久了，為什麼不直接用 Slurm 或 Kubernetes 呢？Slurm 其實蠻不錯的。

Slurm 是二十年前從 HPC（高效能運算）領域發展出來的，本來就是為了進階排程能力而設計的，我會說它是目前最好的配額（quota）和優先順序管理系統之一。但它其實並不太支援以容器（container）形式做隔離，雖然你可以在上面加裝像 Pyroot 之類的容器層，但它本來就不是為此設計的，也從來不是為了「serving」而生，比較偏向批次（batch）工作。而 Kubernetes 大概十年前開始興起，在微服務（microservices）領域非常受歡迎，某種程度上非常有彈性、就是為雲端而生的，但它的學習曲線非常陡。如果你把 Kubernetes 丟給一個研究員，他大概會說：這是要怎麼用啊？

他們大概只能去問自己的 agent 幫忙搞定。而且 Kubernetes 也缺少很多 AI 需要的基本元件（primitive），特別是像 gang scheduling 這種功能，一樣得靠像 Volcano 這類排程器加裝上去。但要讓 Kubernetes 真的適用於 AI 其實很困難。更重要的是，這兩者都是單一叢集的管理系統，還是沒有解決「我手上有 10 個不同的叢集在跑，該怎麼管理」這個問題。所以真正缺的不是一個更好的排程器，而是能同時管理這些不同排程器和平台的東西。所以我們的目標不是要取代 Kubernetes，它們在自己擅長的事情上做得很好。我們想做的，是補上這中間的缺口──讓你可以把訓練、serving、沙箱等各種工作負載，跑在分散於 Kubernetes、Slurm 等各處的運算資源上。

所以我們的想法是，如果能有一個開放、統一的運算層，可以最佳化可用性（availability）、判斷一項工作最適合跑在哪裡、處理它的執行，而且做這一切的同時，讓你的工作負載完全不需要知道底層是什麼，這樣就能為整個生態系帶來很大的價值。

這正是我們在 SkyPilot 一直在打造的東西。這是一個完全開源的平台，讓你不管在哪裡都能用你手上的 AI 運算資源。你可以自帶你原本的框架，比如 Ray、White Arch、OpenEnv、Unsloth，你自己的框架都可以，然後把工作提交給 SkyPilot，跟它說「嘿，我需要 8 張 B300 來跑這個工作」，接著 SkyPilot 就會負責整個協調工作：它會看你手上的運算資源，你的 Slurm 叢集、Kubernetes 叢集，甚至雲端虛擬機，然後負責協調這些資源、執行工作、把記錄和結果回傳給你等等。SkyPilot 這個專案，其實就是在離這裡沒幾棟樓的柏克萊 Soda Hall 誕生的。

它是開源的，社群相當活躍也很健康，有很多人在用，也有很多人在貢獻。目前也被一些業界最大的公司採用，而且它其實根植於我們當年在 Sky Computing Lab 做的研究。

那我快速帶大家看一下 SkyPilot 到底是怎麼運作的，其實非常簡單。要在 SkyPilot 上拿到運算資源最簡單的方法，就是打一句 sky launch，告訴它你想在哪裡跑、需要什麼資訊，然後說明你需要哪些 GPU。如果我想從 Kubernetes 切換到 AWS，只需要改一個參數（flag）就好。GPU 也是一樣，你的應用程式當然還是需要知道底層在跑什麼，但你只要改一個參數，就能輕鬆切換要配置的 GPU 型號。

那如果你想做更複雜的事呢？不只是配置一些 GPU，而是要跑一個複雜的工作，像是一整套強化學習流程，我們有一個叫做 job group 的抽象概念，這是一種宣告式（declarative）的規格，你可以說「我有一個 rollout server，需要某些資源，需要跑這些指令」，接著「我還要拉起，比如說一千個沙箱來跑這些東西」，我可能還需要，舉例來說，讓 rollout server 跑在 H100 上，而訓練端跑在 B200 上。把這些都寫好交給 SkyPilot，SkyPilot 就會幫你把整個工作負載的協調都處理好。而且在這麼做的同時，它也提供了一些貼心的功能。

舉例來說，它會幫你做服務發現（service discovery）、生命週期管理（life cycle management），如果其中一項工作失敗了，不代表整個執行都要失敗，它只會幫你重新啟動那一個工作。

好，我們剛剛一直在講訓練，但 serving（服務推論）同樣重要，而且 serving 也能從這種統一平台中受益。具體來說，你可以拿到橫跨所有叢集的容量。與其只在一個叢集裡開一批執行個體，你可以讓 SkyPilot 橫跨你所有的叢集來跑推論；當某個地方發生故障時，SkyPilot 可以無縫把你的副本（replica）搬到還有容量的地區。而讓所有工作負載都跑在同一層底下的另一個好處是，你其實可以在同一批機器上，同時跑推論和訓練，做出很多有意思的事情。也就是說，你可以用同一批 GPU、同一個巨大叢集來跑你的工作。

舉例來說，如果推論的請求量突然暴增，SkyPilot 可以動態地把資源從訓練重新分配到推論上，也就是先把訓練工作搶佔（preempt）掉，你的 checkpoint 機制會處理好一切，不會遺失資料；等到推論的尖峰過去之後，它會自動把推論規模縮回去，然後繼續訓練。很好。我想再強調一次，這一切都是 BYOC（bring your own compute，自帶運算資源）。並不是說你要把信用卡交給 SkyPilot，讓它幫你買運算資源；而是你自己從雲端供應商那邊帶來自己的運算資源、自己的資料，一切都跑在你自己的環境裡。我差不多要收尾了，但簡單來說，我們的想法並不是要重新發明或取代 Kubernetes 或 Slurm。

它們在自己擅長的事情上做得很好。我們真正需要的是一個統一層，能幫你補上工作負載和你手上所有叢集之間的落差。好，就講到這裡，非常謝謝大家。
