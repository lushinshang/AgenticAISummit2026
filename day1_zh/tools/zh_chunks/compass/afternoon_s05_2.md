好的，接下來有請加州大學柏克萊分校的 Nilou Salehi 教授，她要談的是代理型（agentic）推理，也就是需要把資訊壓縮成可執行的推論結構。

我叫 Nilou。我是一間叫 Across AI 公司的共同創辦人兼執行長，同時也在這裡擔任教授。我今天要講的主題是：我們大家這幾年來一直在解決的整體問題，其實就是「壓縮資訊」。因為說到底，這正是模型在做的事，也是硬殼在做的事。我們一直在尋找不同的方法，把大量的資訊壓縮成一種可執行的格式，就像一個 transformer 模型是可執行的，能預測下一個 token 一樣。接下來幾年會發生的是，我們會發展出愈來愈多架構，能用更複雜的方式做到這件事。而我們首先要解決的其中一個問題，就是：各種不同類型的流程分別是什麼？針對每一種流程，最適合的架構或硬殼又是什麼？

我想分享一個我們用得非常成功的做法，叫做推理圖（reasoning graph）。推理圖就是一張由代理人組成的圖，圖中你看到的每一個圓圈都是一個代理人。我們發現，對於某些特定流程──尤其是那些需要重複執行、而且要求非常高一致性的流程──這是一種非常好的架構。運作方式是這樣：在最底層，有一層代理人負責連接到所有原始資料所在的各個系統，這些代理人做的事就是理解那些原始資料。再上一層，是負責推理的代理人層。最後，還有一層代理人，負責在對的時機採取對的行動。

所以任何一條從最底層一路連到最頂層的路徑，就是一種可能的推理路徑。今天我們也看到同樣的概念以不同形式出現，例如你可以平行執行這些路徑，也可以用某些方式來最佳化它們。接下來的問題就變成：你要怎麼建立出這樣的一套系統？今天其他幾場演講中也出現過類似的概念。而這件事必須是由一個代理人來完成的。所以我們會愈來愈常看到，代理人與硬殼之間出現這種「握手」關係，這個代理人被訓練得非常清楚該如何與那個硬殼協作。而這些不同的架構，會分別適合不同類型的流程。我們投入很多心力的其中一種，是所謂的「架構師代理人（architect agent）」，它適用於那些需要持續、高度精確執行的流程，例如財務流程、供應鏈，或是任何公司需要一而再、再而三持續運作的流程──這類流程雖然本質上是非確定性的，但仍然需要有智慧、需要高度一致，也需要能被解釋。

這樣做出來的結果是非常高的一致性。我們在執行這些流程時，準確率經常穩定超過 95%。在某些範例或基準測試中，就連 Fable 也只能達到大約 40% 到 70% 的準確率。同時我們也得到非常高的速度。在產生這個硬殼的整個過程中，完全沒有寫任何自訂程式碼，全部都是架構師代理人與這個特定硬殼協同運作的結果。因此我們可以在幾週之內就推出新的應用案例。而這個架構中最重要的部分，是那個模型的智慧與權重會不斷複利累積：每一次架構師接手一個新的應用案例、為它建立推理圖並學會怎麼做，它就會做得更好。這種模式我們會愈來愈常看到，也會出現在各種不同類型的流程中。

我想舉一個我們用這套架構「代理人化」的流程實例，那就是發票核對（invoice matching）。規模非常大的公司會收到大量發票，他們得做一個很簡單的決定：付款，還是不付款。他們會收到一定比例的詐騙發票，所以不能照單全付；但也不能拖太久，因為如果沒有準時付款，會影響到整個供應鏈的運作。想像一下，大型公司每個月要處理數百萬張這樣的發票。發票進來後，要對應到一張採購單（PO），還要標準化。中間有非常多例外情況，例如單位可能不同、貨幣可能不同、某些地區有稅金問題。有一個讓我印象很深、覺得很有趣的例子是：如果貨物是液態的，發票金額比採購單金額少到 5% 都算可以接受，但這只限於夏天，因為有些液體會蒸發，這是沒辦法的事。所以這個代理人必須不斷學習，這不是一次性、一次到位就學會的事，也不是只發生在單一場工作階段（session）裡的事，而是持續橫跨很長時間──數月、數週──每次遇到例外狀況，都必須從中學習。就算用 Fable 打造一個基準代理人硬殼，也只能答對大約 40%。這是我們的架構師代理人為這個流程建立出來的推理圖，它由許多代理人組成，包含它們之間的連結方式、指令內容、每個代理人該用哪個模型，每個代理人也都有自己的長期記憶。所有這些決策、所有這些工程上的決定，都是由代理人自己做出來的。而我們在這個真實資料範例上達到的準確率是 99.9%。

第一版推理圖在一週內就上線運作，而且在 96% 的案例中，我們不僅給出正確的決定，還能正確解釋為什麼做出這個決定。這讓某家財星五百大企業處理每張發票的成本，從原本的 5 美元降到 1.5 美元。而最近，就在這星期，我們把成本進一步降到每張發票 10 美分。這就是當你能把學習成果壓縮成可重複使用的結構時，所能達到的進步幅度。

大家好，我是 Johann Schleier-Smith，任職於 Temporal Technologies。今天我要跟大家分享我們對代理型 AI（agentic AI）生態系的看法，同時也介紹一下 Temporal。先舉手問一下，這裡有誰聽過 Temporal，或至少聽說過？好，有幾位。那有多少人實際用過 Temporal？好，那我先說明一下，這會是一個高階概覽。如果你留到這場之後，我們還會辦一場工作坊，讓大家可以動手實作、實際寫程式碼。那我們就開始，先來談談系統。談到系統，我們指的是把一大堆元件組合在一起，藉此打造出某種功能。

而在 AI 的情境裡，這樣的元件非常多。所以我們不只需要實現核心的基本功能，還有一系列所謂的橫切關注點（cross-cutting concerns），像是可靠性──這正是 Temporal 有深厚經驗的領域；效率、安全性、可演進性，這也包含可擴展性，以及能不能順利升級等等。我想稍微深入談談可靠性，因為這正好能說明 Temporal 底層的核心機制。假設我們有一個代理人，這裡以客服代理人為例，負責協助處理退貨，那這個代理人就需要連接到一大堆不同系統：知識庫、庫存、ERP，它需要處理付款，可能還需要處理升級（escalation）流程，也需要能夠寄送電子郵件。而為了讓這一切都能可靠地運作，我們得做什麼？我們需要在很多不同的地方加入重試機制；可能還需要排隊機制來處理負載；需要狀態管理，才能追蹤整個流程從頭到尾的進度；而這些都是可能出狀況的地方，所以不管是誰在打造這個系統，都得想辦法處理好這些問題。傳統上，軟體會把應用程式的關注點──也就是業務邏輯──跟系統層面的關注點（例如可靠性，以及我們剛提到的其他系統層面問題）交織在一起。

如果從這場演講中只能記住一件事，那就是 Temporal 讓一件事成為可能──那就是「持久化執行（durable execution）」這個模型。它讓你可以把程式碼寫成一邊是系統邏輯、另一邊是應用程式的關注點，並且真正把兩者分離開來。Temporal 這個開源專案本身能讓你做到的是：打造出「不會崩潰」的應用程式。它是開源授權，採用 MIT 授權條款，你可以用多種不同的資料庫來支援它，例如 Postgres 或 Cassandra，也有雲端版本可用。但這裡的關鍵是，它讓你可以用一般的程式語言寫一般的程式碼──Python、TypeScript，任何語言都行──就能得到不會崩潰的執行能力。

那當系統崩潰之後，要怎麼恢復呢？基本上要拿回那個狀態有兩種方式：你可以把它存起來，或者重新計算它。用 Temporal 的話，你可以把它想成──我們在工作坊會講更多細節──就是一些很簡單的註記，你可以標在程式碼上，說「這裡我要你重新計算」、「這裡我要你儲存狀態」，大概就是這樣。如果真要說有什麼訣竅，這就是那個訣竅。還有其他很酷的東西，例如用一般程式語言的基本元件就能做出分散式系統，這也蠻酷的。不過我想花點時間談談外面那些公司──也就是我們的使用者、我們的客戶──是怎麼使用 Temporal 的。這位是 Venkat，OpenAI 應用程式基礎架構部門副總裁。

其中一個值得一提的應用是 ChatGPT 的圖片功能，這裡面有一整串步驟，必須全部可靠地依序完成，才能產出那張圖片。這是 Temporal 與 OpenAI 合作中很值得一提的案例之一。網頁版的 Codex 是另一個例子，但其實還有一整系列的應用，從基礎架構的控制平面，到資料連接器（例如建立與維護 RAG 索引之類的工作），再到最後傳統的商業流程都有。而且不論是在 Nvidia、Cursor、SpaceX，還是 Lovable、Replit，Temporal 都被廣泛用在整個技術堆疊中，用來實現代理型 AI。接下來我想深入分享幾個觀察，說明我們是怎麼看待這件事的，以及我們與生態系裡各家公司合作後學到了什麼。

我們需要提供這樣的功能，對吧？這是一個代理人，而「代理人」這個詞對不同的人來說意義不太一樣。在商業情境下，它基本上就是某個能把事情完成的系統。而我們花很多時間思考的──尤其是在我所屬的 AI Foundations 團隊──其實是：什麼才是正確的抽象方式？這種代理型 AI 工作負載會帶來哪些取捨？我們要怎麼切分這些取捨？哪些地方我們該直接選定一個方案，哪些地方或許該提供一個可調整的旋鈕？針對這類工作負載，我想分享幾個我覺得特別有意思的觀察。我不會把這些內容全部念過一遍，但就先從語言模型（LLM）本身談起。

我想說的是，這其實跟我們過去在系統領域處理過的其他工作負載很不一樣，所以能重新思考這些抽象方式其實蠻有趣的。先講「非確定性」：這代表你每次呼叫語言模型，都需要驗證並儲存它的回應。但有趣的是，這也有另一面──它同時也帶有一種模糊性，對輸入其實相當寬容。這正好是它輸出結果不一定百分之百確定的另一面。再來是安全性，這從威脅的角度來看很有意思。大家常會想到對抗性輸入，像是提示注入（prompt injection）與對齊（alignment）問題，但當你在思考代理人時，另一個很棒的威脅模型其實就只是「判斷失誤」，對吧？

因為這種事真的會發生──那個 `rm -rf` 事故，這其實是意外造成的，不是刻意的──而這正驅動了我們很多設計上的考量。而從執行輪廓（execution profile）的角度來看，因為你正在跟真實世界互動，這正是你需要仔細記錄狀態、確保萬無一失的地方，同時也會有突發性（bursty）負載，這就需要無伺服器（serverless）之類的架構來因應。另外，我們與整個生態系裡各家公司合作後得到的另一個觀察是：其實存在一整個「代理程度光譜」，而針對特定應用、特定功能的正確解法，可能落在這個光譜上的任何位置。

而事實上，代理程度愈高，並不代表就一定愈好。大家一想到代理人，往往會想到所謂的「第三級」，也就是一個代理型迴圈──由語言模型自己決定接下來要發生什麼事。但如果往左邊看，看看「第一級」，其實有大量的應用──像是摘要之類的工作──靠一般程式碼來驅動控制流程，只在非常特定的節點插入語言模型，就能把事情做得很好。這樣可能非常可靠，如果這樣就能把工作完成，那這可能就是正確的解法。而在光譜的另一端，我們甚至看到「自我演化代理人」，這在一些硬殼裡已經開始出現。

這樣做自有其道理，但你也可以想想，這未必就是最適合那項工作的解法。而我們在思考 Temporal 針對代理型 AI 的抽象設計時，其實真正想的是：如何讓你能夠自由調整、在這個光譜上來回移動，而不必重寫整個應用程式。所以我們今天要分享的其中一項，是 Temporal Agent Harness。這目前還不是正式支援的產品，但如果你去 GitHub 上啟動這個 repo，希望不久之後就會是了，我等一下也會放上 QR code。這是一組建立在 Temporal 核心「持久化執行」抽象之上的抽象層，讓你能更輕鬆地打造出實用的代理人，不論你想打造的是什麼。

所以我們讓你能夠自由插入內部的硬殼，可以是像 OpenCode 這樣的程式撰寫代理人，也可以是像 OpenAI Agents SDK 這種東西──它也有很多有趣的沙盒（sandboxing）功能──或是 Pydantic AI，這些都可以。我們真的很努力去擁抱整個生態系。你可以插入自己的工具。而且這整套設計的重點，就是讓你能自由混搭這些抽象元件。也就是說，如果你想透過 Slack、Teams 之類的介面跟它互動，都可以。這邊只是一張 OpenCode 工作階段的畫面截圖，當時我正在裡面修一個簡單程式的錯誤。因為我是用 agent harness 來執行的，我不只得到了持久性、可靠性──如果我想要大規模執行的話這很重要──而且還額外得到一些東西，其實這根本就是整套方案本身自帶的一部分。

我得到的是可觀測性（observability），可以深入去看代理人在各個步驟中在推理什麼、過程中發生了哪些工具呼叫、哪些人工核准之類的事情。而這正是當你認真思考自己引入的抽象設計時，能得到的好處。到這裡我先告一段落。也歡迎大家留在這間會議室參加接下來的場次，那會是一場工作坊，讓大家可以動手實際操作 Temporal。
