好的，我看看能不能把這個拿下來。太好了。很榮幸能擔任這場的第一位講者。今天我很興奮能跟大家聊聊如何為編碼代理人擴展強化學習（RL），以及過去一年我們在 Cognition 建立研究計畫的心得。我是 Silas，是創辦團隊的一員，也負責 Cognition 的研究工作。我們以打造 Devin（世界第一個 AI 軟體工程師）聞名，另外還有大約一年前收購的 WindSurf。今天要講什麼呢？我想跟大家分享我們的擴展歷程，也就是四次野心逐漸加大的訓練回合。特別是，我們是怎麼挑選問題的？在當時的算力與團隊規模下，我們下了哪些賭注？

還有一路上解決的一些挑戰，像是多輪訓練、平行工具呼叫、非同步 RL，以及熵崩潰（entropy collapse）。這是我挑出來的四個專案，我會照順序講下去。Kevin，32B，是我們團隊謙卑的起點。當時基本上剛起步，只有幾位實習生，加上大概 32 張 H200 GPU。我們在想，用這樣的算力能做出什麼真正有趣的事？我們第一個想法很簡單，挑一個非常聚焦的問題，看看能不能用 RL 在這個問題上做出成果。我們選的是 KernelBench，它當時才剛推出，是一個用編碼模型撰寫 CUDA GPU 核心（kernel）的基準測試。

概念上是這樣的：你拿到一個 Python、PyTorch 函式，必須寫出一個能讓這個函式加速的 CUDA 核心。結果證明這真的可行。我們實作了 GRPO 並讓它跑起來。我覺得當時我們很想探索的一件有趣的事，是多輪代理型訓練長什麼樣子——大概一年前，這還算相當瘋狂、相當新穎的做法。有趣的是，從這張圖可以看到，多輪訓練的表現超越了單輪訓練。而且我們光靠這個 QEN 32B 基礎模型，就能在這個基準測試上訓練出當時最頂尖的模型，甚至比 o3 還好，這感覺相當厲害。

關於訓練穩定性，我想分享一個有趣的小故事，作為這個專案的一個亮點：我們碰到不少不穩定的問題要處理，後來發現一個很有意思的不穩定指標，我們稱之為「not okay 比例」。基本上，這個模型的思維鏈（chain of thought）總是以「okay」這個詞開頭，這是這個模型一個奇怪的癖好。而隨著訓練推進，這個思考過程會逐漸變得比較瘋狂、比較絕望。這裡有幾個例子，一開始是「好，各位，我需要最佳化這個三維張量矩陣乘法」，到訓練後期變成「好，我的天啊，我得把這段程式碼弄好」。

而不穩定的代理指標，基本上就是我們在量測這個 not-OK 比例，它是訓練回合最終走向發散的一個早期指標。這也是模型在訓練中偶爾會「暴走」的一種有趣呈現方式。在這之後，我們打造了 SweGrep。我們想再更有野心一點，打造一個真正實用、能放進產品裡使用的代理人。編碼代理人的一大重點，是找到正確的檔案。我們想，或許可以解決這個子問題，讓它更便宜、更快。大致的想法是，你可能對某個程式碼庫有個問題，比如「VS Code 是怎麼有效率地實作檔案監控（file watching）的？」，而目標就是找出與這個問題相關的檔案清單。

概念相當簡單，好處是這是一個乾淨、可驗證的獎勵，因為你可以直接用 F1 分數去比對檔案清單。於是我們再次用 RL 訓練了一個代理人，並建立了自己的評測基準，稱之為 code search eval。很開心看到我們又一次在這個特定評測上訓練出當時最頂尖的模型，那時大概是 Sonnet 4.5 的時代。另一個很酷的地方是，這些模型可以跑得超快，因為我們用的是 Cerebras 晶片。SweGrep Mini 特別能跑到每秒約 3,000 個 token，相當猛，看模型跑起來也很神奇。後來我們把它放進了 WindSurf。

從科學角度來看，這裡最有意思的發現——當然細節很多——是平行工具呼叫。基礎模型以及當時大多數模型，都是一次呼叫一個工具、依序執行。當時剛好是 Sonnet 與 Anthropic 開始做平行工具呼叫的時期，例如你會看到 Sonnet 一次呼叫兩、三個工具。我們非常想最佳化任務的端到端延遲，也就是盡可能讓更多事情平行進行。所以 SweGrep 有時候一次會跑八個工具呼叫，這確實大幅提升了端到端延遲表現。從這張圖可以看到，隨著訓練推進，分數在上升，每一輪的平行工具呼叫數量也大幅增加。

在 SweGrep 之後，我們決定開始打造真正的前沿編碼模型，可以用來完成端到端任務。我會重點介紹其中兩個，當然還有更多，像是 SWE-1.5、SWE-1，但 SWE-1.6 與 SWE-1.7 是我們今年稍早推出的最新兩個版本。到這個階段，我們開始量測真正的編碼評測，像是 SWE-Bench Pro，試著看看如何在真實的編碼問題上提升端到端表現。SWE-1.6 讓我們相當自豪，當時在這個基準測試上追平了 Opus 4.5。神奇的是，同樣的基本原則依然適用——當然你得用更多、更難的資料——但在整個訓練回合中，解題能力可以大幅擴展。

在我們內部一個可驗證軟體與訓練任務的評測上，經過其中一個 RL 訓練回合，我們的分數從 52% 進步到 68%。另一件很酷的事是，模型實際上學會了思考更久。一開始，它平均可能只思考大約 4,000 個思考 token，但這個數字在整個訓練回合中大致翻倍。這也讓我們學到，穩定的訓練、良好的演算法究竟意味著什麼。因為事情顯然不像拿資料去跑模型那麼簡單，中間會出現各種崩潰與穩定性問題。這裡可以看到兩個例子：基本上，當我們在調整演算法時，可能訓練了 200 步之後，模型就崩潰了。

接著我們會去診斷問題，找出根本原因，重新啟動之後，很有趣的是，訓練軌跡幾乎會依循一模一樣的路徑，但到了原本崩潰的那個點，現在變得更穩定，可以繼續往下走。所以每一次演算法的改進，都能把訓練的可持續步數從 200 步推進到 300 步，再往後推。

我覺得這個專案裡另一件對我們來說很新穎的事，是非同步 RL，以及我們如何在越來越長的 rollout 中把吞吐量最大化。基本概念是把訓練器（trainer）和 rollout 分開：rollout 只負責把一批批的資料組（group）持續送進資料緩衝區，訓練器則在資料緩衝區填滿時把資料吸收進去，等它完成一個訓練步驟後，就會把權重更新送回給 rollout。等一下講到 SWE-1.7 時，我會再回來談這個部分。

非同步 RL 的一個缺點是，你的訓練策略（training policy）跟推論策略（inference policy）可能會出現落差。也就是說，你收到的一批資料，可能來自幾步之前的推論策略，這就是我們所謂的「staleness（過時程度）」——推論策略落後訓練策略的步數。有趣的是，這其實形成一個循環：你把演算法的訓練穩定性改善得越好，就能容忍越高的過時程度。尤其在剛開始的時候，我們幾乎完全無法容忍高過時程度，但隨著時間推進，我們逐漸把這個上限往上推。這裡可以看到我們比較的兩個訓練回合，黑色那條訓練曲線能容忍的平均過時程度高得多，這也讓我們能充分利用推論引擎的算力。

所以更好的演算法讓我們能達到完整的算力利用率。這就帶到了我們最新的模型 SWE-1.7。這裡可以看到，現在的評測已經不再只是一維長條圖，而是這種二維的成本對效能圖。我認為值得一提的是，這個模型在同量級中表現特別突出。我們訓練時用的基礎模型是 Kimi K2.7，就是圖上那個位置，另外還有同樣基於 Kimi 的 Composer 2.5，以及規模差不多的 GLM 5.2。就同量級來說，它的表現相當亮眼，能跟許多規模大得多的模型競爭，成本卻便宜許多。

那麼，做到這件事需要哪些條件？我認為，尤其是當你想從這種比較小的模型裡榨出最多效能時——當然一兆參數已經不小，但相較於一些前沿模型動輒數兆參數，這還不算頂級規模。當時外界一直傳言說 RL 已經碰到瓶頸，重點都轉回預訓練了。但我們想試試看能不能再往前推一點。此時我們卡在熵崩潰（entropy collapse）這個瓶頸上。RL 進步的關鍵，說穿了就是你的資料組裡有沒有多樣性，以及有沒有發現新的行為模式，而這些都可以用我們所謂的「熵（entropy）」來衡量。通常在整個訓練回合中，熵會隨著時間下降。

最終，熵會崩潰，這時候你就撞上了這次 RL 訓練回合的天花板。我們當時真的很苦惱，因為分數再也提升不了。不過好消息是，只要持續調整 RL 的訓練配方——詳細內容建議大家去讀我們的技術報告——我們找到了一套配方，讓熵幾乎是「感受不到的下降」。雖然它還是會隨時間慢慢下滑，但斜率平緩很多。這樣一來，我們就能把效能再往上推進不少。

另一件很酷的事，是我們如何跨三大洲進行訓練。我們當然想把算力規模越擴越大，但現在要找到夠大、夠連續的訓練叢集其實真的很難，尤其是在你需要的時程內——有些叢集甚至得提前一整年預訂。所以我們發現，反而更容易找到散布各處的小塊算力，這裡一個小叢集、那裡一個叢集。最後的結果是，這次訓練回合橫跨四個國家、三大洲，包括澳洲、馬來西亞、加拿大和美國。我剛才會說之後要回頭談非同步 RL，原因就是：能做到這件事，唯一的原因就是非同步 RL。這次訓練回合的大致架構是，我們有一個訓練叢集，這次是在美國，另外還有很多分散在世界各地的 rollout 叢集。整個系統彼此溝通的方式，是推論叢集把訓練批次資料送到訓練叢集，訓練叢集再把權重更新送回推論叢集。

而我們之所以能在全球範圍做這件事，是因為需要傳輸的資訊其實非常稀疏（sparse）。在 RL 裡，權重更新是很稀疏的，訓練批次資料本身也只是 token 而已。

講到這裡，我想用回顧我們的理念來做個總結：我們並不真的相信這需要多複雜的東西、多花俏的點子。研究上的許多進展，其實就是把簡單的事情，用擴展規模的方式扎扎實實做好而已。這就是我想說的，非常感謝大家邀請我，接下來交還給 Kamal。

非常謝謝你，Silas，太精彩了。這不完全是背書，不過我自己確實常常在 Cognition 用 Devin，所以要謝謝你的努力。好的，接下來，喔，謝謝。接下來是 Dhruv Batra，他是 Yutori 的首席科學家兼共同創辦人，掌聲歡迎 Dhruv。

好的，謝謝邀請我。我是 Dhruv，Yutori 的首席科學家，也是共同創辦人之一。跟一般的演講不同，我不打算只是跟大家介紹公司，我想聊一個完全不同的主題。我想跟大家談一個特定的論點，以及它的反駁論點。這個論點是：網路上有一個很流行的說法，說 AI 代理人將會成為網路上行動的主要驅動者，而不是人類——它們會替我們訂會議、訂預約、買東西、取得資訊等等。這是主張本身。接下來，第二步，當你問提出這個主張的人「要怎麼做到」，通常得到的答案是：這是因為網路將會被「代理人化」（agentified）。

也就是說，網路會變得對代理人友善。你再問「要怎麼做到」，得到的回答通常是：透過 API，讓我的代理人、你的代理人、我們企業的代理人，透過 14 種不同的標準彼此呼叫，像是 MCP、web MCP、支付協定等等。今天我想提出一個非常明確的論點：前兩步是對的，第三步是錯的。這個論點站不住腳，我會提出一個反駁論點。所以我今天演講的主張是：電腦使用代理人——也就是像人類一樣，靠看畫面、按按鈕來操作電腦和瀏覽器的代理人——才會讓網路變得「代理人化」，而且更精確地說，是讓網路長尾（long tail）的部分代理人化，而不是靠 API。你的網站，那些長尾網站，不會有 API 可用。

為了讓大家更直觀感受這件事，先從這個領域最常見的例子說起：一個消費者或開發者坐在他的 iPhone 前，問「幫我找這班航班」。你會想像幕後有一個瀏覽器使用代理人或電腦使用代理人，去打開 flights.google.com，像人類一樣點按鈕。這在這個領域是極為常見的示範，但其實非常荒謬可笑，因為你為什麼要這樣做？明明有聚合型 API 服務，它就是個資料庫，你可以送出結構化查詢，拿回結構化結果，為什麼要用點按鈕的方式來做這件事？我的主張是，讓我們把這個問題推廣一下。

假設我問的不是這個問題，而是：我在計畫一個晚上跟朋友的聚會，我想知道的是，我指給你看一間餐廳，問你「這間餐廳的菜單上有沒有無麩質（gluten-free）的品項？」大家想像的情境是，某天會出現 myfavoriterestaurant.com/menu 這樣一個端點，你可以直接用 curl 呼叫，用自然語言查詢，或是篩選「給我菜單上無麩質的品項」。對於認為這是現實、或即將成真的人，我想讓大家看看真實的餐廳網站長什麼樣子。我的投影片之後會放到網路上，今天先讓大家看幾個簡單、中等、困難模式的例子。

簡單模式時，大家想像的是這種網站，上面有一些文字可以讀。中等模式，你拿到的是菜單的 PDF 檔。困難模式，你拿到的是一整排菜單頁面的個別掃描圖，就這樣拼湊在一起，畫質很差，甚至沒有做 OCR。而經營這些網站的人，是各地的小企業主，他們就存在於某個角落。舉例來說，光是歐洲某一個國家，就有大約二十萬個自己維護網站的小企業主。而大家想像的是，明天，或者未來五年內，這些網站都會被徹底革新，變成能讓你的代理人存取的閘道。我的主張是：這件事不會發生。我們苦苦等待的援兵，並不會出現。

網路是極度長尾的。單一網站或許價值有限，但整條長尾累積起來的價值非常龐大。而基礎設施的變化非常緩慢。到這裡，通常大家會回應：好吧，那我們直接讀程式碼好了，我們有編碼代理人，直接讀 HTML 就行了。接下來我想用另一個例子，說明為什麼這個論點也站不住腳，為什麼這樣做不可行。假設你想知道某個電商網站上，一顆 24mm 的鋨（osmium）方塊有沒有現貨。這是個很單純的查詢，有一個商品頁面，你只需要知道有沒有貨。你往下滑，看到一個數量下拉選單，用肉眼看畫面的你我都能看出，其中三個品項已經售完、不可購買，只有一個品項有貨。但當你派代理人去讀這個頁面的 HTML 時，會發現這個下拉選單本身完全沒有提到數量。HTML 裡的選單元素確實有各品項的描述，但完全沒有數量資訊。為什麼？懂 JavaScript 和網頁技術的人這時大概都在搖頭：你們這些傻瓜，早該猜到會這樣。實際上，幕後有一個查詢：頁面載入時，會發出請求拿到一個 JSON 物件或字典，裡面填的是當下這家店有什麼庫存、數量各是多少；而當你點下拉選單時，是另一段程式碼在決定要顯示成灰色（不可選）還是彩色（可選）。這是因為——雖然我們看到的是畫面——但瀏覽器本質上是一個渲染引擎，對做過遊戲技術的人來說，最貼切的比喻就是：瀏覽器其實就是一個渲染器，底層有素材、有程式碼，最終產生的是像素。所以我的主張是，網路是為了人類的眼睛而建的，那才是真相的來源，因此機器也必須靠「視覺」來操作。我們在 Yutori 寫過一篇部落格，叫做「網頁代理人的苦澀教訓（the bitter lesson for web agents）」——如果你不去看像素，你就只能被困在特徵工程（feature engineering）裡，永遠碰觸不到網路的長尾。

大家午安。好，我打算用五分鐘，把我們過去兩年在微軟打造代理人、並實際運行的心得濃縮講完，來試試看。看來第一個心得就是：在「代理人對 AI」這件事上，壓縮（compression）確實存在，我會盡量在五分鐘內講完。今天我要談的是一個「代理人操作、人類治理」的世界。這幾十年來，人類一直靠軟體系統來工作——我們建立儀表板、指標、告警和自動化，最近則開始用 Copilot 來完成工作，但終究還是人在操作。我們要怎麼把這件事「反過來」？今天我要講的故事，就是我們在微軟如何把這件事反過來做，以及大家可以帶走的心得。

好，如果只能用一張投影片濃縮過去這幾年學到的東西，就是這張。我今天要談的第一件事是「零營運（Zero Ops）」，也就是我們的終點。這不是要把人從營運中移除，而是要把「營運」從人身上移除，後面的投影片會說明這是什麼意思。模型是可以替換的，你可以換模型，模型每天都在進步，但你的上下文（context）、治理（governance）與工具不是可替換的，所以要把資源投入在這裡。要讓一個代理人真正有用，光靠模型本身無法提供足夠的智慧，你必須能夠治理它、控制它，還要給它正確的上下文，而治理正是這一切的關鍵環節。

企業很喜歡從中得到的智慧，但如果他們無法控制這個智慧，就贏不了他們的信任。談到信任，你需要有可驗證的指標，讓你能驗證代理人做了什麼、結果是什麼。說到這裡，讓我進入投影片的核心：什麼是 ZeroOps？ZeroOps 是一個願景，代理人會開始承擔越來越多的營運工作，把瑣碎的工作從人類身上拿走，讓人類去做更有影響力的事，像是創新或治理之類的事，這是一個終點，過程則是要經歷爬、走、跑、飛這幾個階段。

而「飛」不只是單純執行，不只是代理人做了某件事而已，而是你讓代理人去做一件事、驗證結果，再把結果提供給人類確認。舉個例子，如果一個代理人正在修復某個 API 因效能變慢而產生的迴歸問題，它去建立了一個 PR，這很簡單，PR 建好了，很好。但更好的做法是：代理人不只建立 PR，還把 PR 部署到測試環境，驗證結果，確認這個迴歸問題確實消失了，效能也恢復正常。這就是我們所謂的「以結果為導向的工程（outcome-based engineering）」，人類不再逐一審查每個 diff，而是審查結果。

就像我說的，上下文就是一切，模型不是護城河，那什麼才是護城河？是你的原始碼、你的正式環境遙測資料、你的組織知識，以及你賦予這套系統的技能與工具。做到這些之後，代理人就能自動化，幫你把事情完成。

代理人必須被信任。而要能信任代理人，企業必須能夠稽核、控制、評估、有信心地回滾，並用證據證明代理人做的確實是它該做的正確的事。少了這些，企業就不會願意採用。我看到只剩一分鐘了，所以最後兩張投影片：你需要有權限機制，指標是驗證結果的重要方式，如果沒有權限機制，你就沒辦法讓企業大規模部署代理人。談到規模，這就是微軟導入 Azure SRE 代理人的故事，你不必從零開始打造這一切，這些功能都已經內建在產品裡，我剛才講的一切，其實都已經內建在產品當中了。
