那麼廢話不多說，我們來聽聽他要談的探索、模型與代理人。Saurabh，謝謝你。很高興能來到這裡，我以前就是在柏克萊念書的，所以回來這裡感覺特別好。我今天要談的是 AI 從模型演進到代理人、再演進到探索的過程，以及背後相關的基礎設施意涵。大家應該都很清楚 AI 的採用幅度有多驚人——從三、四年前單一的聊天機器人，到現在幾乎已經是半自主甚至自主的代理人。底下的數字反映了這種採用規模與影響力。Kaggle 有一門「五天學會代理人」的線上課程，去年秋天開課時，有 150 萬名使用者註冊。

如果你去看代理型任務的成本，會發現它所需要的推論運算量，比非代理型工作負載高出 10 到 100 倍。所以採用率在上升，每次互動所需的運算複雜度也在上升。從 Google 的角度來看，這帶來的結果是，我們每個月處理 3.2 千兆(quadrillion)個 token。千兆是個後面跟著很多個零的龐大數字，換個方式理解：一千兆大約等於地球上每個人各寫一部小說的字數。也就是說，Google 產生的 token 量，相當於這個世界上每個人各寫了三部小說。規模就是這麼龐大。那麼我們該如何為這個新機會打造基礎設施呢？

這需要整個技術堆疊中不同的組成部分。從最底層開始說起：我們有 AI 超級運算機(AI hypercomputer)，裡面包含 GPU 與 TPU。在此之上，是世界級的研究與前沿模型。接著我們需要資料，讓這些模型或代理人能做出有意義的事。當這些代理人開始執行有意義的任務時，安全與防禦方面既是巨大的機會，也伴隨風險，所以我們需要代理型安全與代理型防禦機制。再往上，我們需要一個平台，讓大家能以便宜、高效、有效的方式重複運用這些能力，這就是平台這一層要處理的事。最後，則是端到端的代理任務團隊，能真正替你完成事情。

要從 AI 中榨取最大價值，整個堆疊需要做協同最佳化。時間有限，我沒辦法逐一詳談，但我會快速帶大家看過其中幾層。Google 在 TPU 上已經投入超過十年，包括液冷技術與共享記憶體等創新都是這段期間的成果。最新一代的 TPU 是 TPU v8。這是我們第一次把主線拆開——就像 Peter 在前一場演講中提到的——分成 8T(用於訓練)與 8I(用於推論)兩個版本。接下來我用一些比較數字，讓大家了解 TPU 進步的幅度。

這張表比較的是目前這一代 TPU(V8)與上一代——也就是一年前剛推出、目前仍是主力機種的 Ironwood TPU。舉例來說，左邊這張表可以看到，單一 pod 可提供的 FP4 exaflops 高達 121 exaflop，這是每秒運算量非常龐大的數字，比前一代大約提升了 3 倍。同樣地，在記憶體頻寬方面，一代到下一代之間也有 2 倍到 4 倍不等的大幅躍進。在訓練——不好意思，是在推論方面，右邊的表可以看到，因為推論需求正快速增加，單一 pod 可提供 11.6 exaflops，是前一代的 10 倍。

記憶體方面同樣有顯著的躍進。那我們拿這麼多 TPU 要做什麼呢？Google 自己當然大量投入使用，現在也有很多其他公司利用 TPU 訓練自己的模型。Google 用它來訓練 Gemini 系列模型，包含 Pro、Flash 與 Flashlight。影像與影片生成模型，像是 VO 與 Imagine，也是用 TPU 訓練的。世界模型(World model)是我們一個全新且令人興奮的領域，Genie 模型也是在 TPU 上訓練完成。AlphaFold 這個蛋白質摺疊預測模型，以及用來訓練、打造下一代 TPU 的 AlphaGo 和 AlphaChip，同樣都仰賴 TPU。從某種意義上來說，這就是用 TPU 來設計 TPU。

這些應用都大量仰賴我們的 TPU 基礎設施，無論是訓練端還是推論端皆然。有了硬體與模型之後，接下來就需要一個平台，讓大家能相對輕鬆地打造代理人。而打造代理人並不只是寫個提示詞這麼簡單，其中有非常多複雜之處。這裡有四個關鍵問題：第一是「建構」，我們提供存取各種不同模型的能力、代理人開發套件(Agent Development Kit)以及 AI Studio 來打造代理人；接著要能「擴展」、「治理」與「最佳化」它們。所以流程是建構、擴展、治理、最佳化。在擴展這一塊，我們提供受管理的執行環境(managed runtime)能力，讓你能從單一代理人實例擴展到數百萬個代理人。

治理變得非常關鍵，因為當這些代理人開始執行有意義的任務時，你會需要像代理人身分識別、代理人註冊機制、代理人閘道這類能力，確保代理人在正確的權限範圍內運作。這些代理人使用的身分系統必須與使用者本身分開，因為代理人能做的事可能超出使用者本身的權限範圍。最後，一旦你把代理人部署上線，就需要對它做最佳化——包括追蹤、模擬、評估、可觀測性等能力，這些都必須具備，才能在正式上線後持續改善代理人。這些都是關鍵環節。此外，Google 自己也會在這整個堆疊之上打造應用。

Google 在這個堆疊之上打造了各式各樣的代理型解決方案。舉例來說，生物學領域有 AlphaFold 與 AlphaGenome；數學領域有 AlphaEvolve 與 AlphaProof；物理與化學領域有核融合模擬(genome fusion)等模型；氣候與永續發展領域則有 AlphaEarth，以及世界頂尖的天氣預測模型 Weather Next。這些全都建構在我們剛剛談到的這個堆疊之上。這裡有幾個實際案例，展現這些最終代理型解決方案帶來的影響。舉例來說，AlphaFold 被廣泛應用在許多領域，包括塑膠污染防治——設計能分解塑膠或抗生素抗藥性相關結構生物學的酵素。

其中一個關鍵領域是「被忽視疾病」(neglected diseases)。世界上有很多疾病，由於缺乏足夠的經濟誘因，製藥公司投入的資源不足。而 AlphaFold 正在做的，就是降低探索這些藥物設計的成本與難度，這帶來了實質影響，例如瘧疾疫苗與藥物傳遞方式的研發。AlphaEvolve 是一個通用最佳化工具，在 Google 內部被大量用於資料中心最佳化，以及其他各種應用，同時也被外部客戶使用。舉例來說，它被用在路線最佳化、量子錯誤更正，也被電子商務公司用來改善需求預測模型，並帶來顯著的成效……

如果仔細想想，這些是截然不同類型的應用，卻在每一項上都帶來巨大的進步。那這一切究竟意味著什麼？隨著我們一路走過這個堆疊、模型持續進步，最終會通向何處？我們相信，最終會走向一個「自主探索循環」(autonomous discovery loop)。這張投影片以生物學為例，但這個概念其實更為通用。我們正在把各個組成模組拼接起來——例如在資料擷取方面，我們現在已經有能消化大量文獻的代理人，AlphaFold 有一個非常龐大的蛋白質資料庫可供使用，還有實驗紀錄。

接著就可以在此基礎上進行假說生成：我們有能針對不同假說進行辯論、產生新解法的 AI 共同科學家(AI co-scientist)。你也可以從建模的角度，利用 AlphaGenome 與 AlphaFold 在幾秒鐘內模擬這些假說並觀察效果。最後則透過 AlphaEvolve 與 Gemini Robotics 來執行濕實驗室(wet lab)測試，查看實際資料結果，並將這些結果重新餵回這個循環當中。這麼一來，原本從資料輸入到成果產出需要花上好幾年的研究週期，現在可以壓縮到幾小時甚至幾天內完成。而這只是其中一個領域——生物學只是一個例子，但這個模式將會影響人類探索活動的幾乎每一個面向。

這是我們正處在的一個超級、超級令人興奮的階段。我的演講就到這裡，謝謝大家的聆聽。

大家早安。我想先聊聊「什麼是代理人」，以及這一切是從哪裡開始的。當現代 AI 時代隨著 ChatGPT 在幾年前開啟時，我們對這些 AI 系統的想像，大致就是人類跟大型語言模型對話，而這個大型語言模型或許能存取某些資料庫。但本質上，那就是「聊天」——人跟 AI 對話。然而這一切已經有了相當大的演變。今天，我們真正在談的是一套完整的自主系統，它由許多模型組成——有些是開放權重模型，有些是專有模型——並具備存取工具、基礎設施、記憶系統、上下文管理、衍生子代理人的能力，以及安全基礎設施。

而發起整個互動的，可能是一個人，在某些情況下甚至不是人，只是一個請求的觸發點。但現在我們擁有的是一整套非常複雜、相互交織的 AI 系統與大型語言模型，在執行某種自主任務。那到底什麼是代理型 AI 呢？噢不，這不是我最新版的投影片。呃，好吧。

看來確實不是。那我就先照著這張投影片講幾句好了。什麼是代理人？代理人不只是一個大型語言模型，而是一個被我稱之為「基礎設施」所包圍的大型語言模型。我所謂的基礎設施，指的是讓大型語言模型真正能做事的軟體——包括在 API 之間調度資料、可能還有型別檢查、以及以規則為基礎的政策執行。換句話說，我們用來包裹大型語言模型、把它變成代理人的這一整套東西，另一個名稱就叫做「電腦科學」。這麼做有很多充分的理由。大型語言模型非常強大，它是我們目前所知，唯一能解決許多過去幾十年來一直無解的各種問題的方法。

我們過去一直嘗試攻克各種棘手的問題，而大型語言模型出現後，確實能解決這些問題。但同時，它們是機率性、非決定性的，這幾乎與軟體的本質完全相反——軟體大多是決定性的，而非機率性的，我們能理解它、檢視它的狀態、對它做出斷言。所以所謂的代理人，其實就是把這兩者結合起來：一方面取用這台機率性、機器學習訓練出來的大型語言模型所具備的智慧，另一方面則用電腦科學的決定性與力量、資料結構與演算法，以及我們花了數十年才學會如何打造出可靠軟體的那些經驗，把它包圍起來。

那麼，一套代理型系統，就是所有這些元素複雜互動下的產物。以一個典型的代理人來說，你會有某種方式來管理餵給大型語言模型的提示詞；通常也會有某種基礎設施，讓大型語言模型能存取工具、可能還要檢查權限。而這一切現在都運行在日益複雜的硬體基礎之上——這個代理人要呼叫的部分軟體，運行在像 GPU 這類加速運算基礎設施上，有些則運行在 CPU 上。現在的儲存階層也變得非常複雜，你有代理人與子代理人，還有需要在這些不同系統之間傳遞的範圍限定資料(scoped data)。

你會看到日益複雜的通訊模式、沙盒環境、安全隔離區(secure enclave)等各種複雜機制。這個平台在硬體與軟體層面都是異質的，更別提模型本身的組合了——你可能有大型模型，也可能有小模型，可能有針對特定領域微調過的專用模型，也可能有透過外部 API 託管的通用型專有模型。這一切共同運作，以解決某個複雜的自主任務。我們把這整套平台稱為「NVIDIA 代理人工具套件」(NVIDIA Agent Toolkit)，它涵蓋部署工具——從 Kubernetes 到託管式基礎設施，再到電腦操作型代理人(computer use agents)。

它也包含我們稱為 CUDA-X 的加速工具集合，例如用於計算流體力學、求解微分方程、或是從 DNA 定序儀器中計算 DNA 序列二次分析的工具。這些原本屬於電腦科學範疇、我們已經有加速解決方案與 API 工具的任務，現在都被賦予了代理能力，讓你的代理人能夠存取這一整套豐富的加速工具。此外還有一系列開放權重模型——像是我們的通用模型系列 Nemotron。我們也有更專精於特定領域的模型，像是機器人與物理 AI 領域，以及專精生物預測模型的 BioNemo。而這一切，同樣都運行在這套非常複雜的基礎設施之上，包括部署與運行各種模型的能力、以及為系統建立沙盒環境以確保你的 AI 不會做出你不希望它做的事，並且盡可能有效率地運行這一切。

我們通常也會在這套基礎設施中內建另一項功能：你會希望能夠擷取系統中流入流出的知識，再用這些資料對模型做後訓練(post-train)，使其專精於你在意的任務。所以我會把這種以離線方式、透過像強化學習這樣的後訓練來改善 AI 的能力，也算作基礎設施的一部分。這種做法常被用來把一個小模型加以特化，讓它在某些任務上跟一個規模大得多的通用模型表現得一樣好。

我還想稍微談談代理型系統與大型語言模型之間實際的介面，也就是大家常說的「代理人外殼」(agent harness)。這個外殼真的很重要——大型語言模型本身封裝了大量智慧，但舉例來說，我的研究團隊最近開發了一套我們稱為 NEMO 物件導向代理人(NEMO Object-Oriented Agents)的外殼。這個構想其實很簡單，如果你掃描這張投影片上的 QR code，就能在 GitHub 上找到這個專案。核心概念是：代理人其實就是一個 Python 物件。這是什麼意思呢？你用 Python 來寫你的代理人，並使用一種特殊的刪節號(ellipsis)語法，基本上就是告訴大型語言模型：「嘿，幫我把這段程式碼補上。」

於是，代理人就能夠真正修改自己——它可以執行自己寫過的方法，也能修改自己的方法；它可以判斷「這是我需要儲存的資訊」，然後把它當作狀態存進這個 Python 物件裡；它也可以把解決某個問題所用的計畫或方式，寫成 Python 中的一個方法，以後再呼叫它。另一個重要的想法是：與其把所有資訊壓縮成字串、塞進一個非常龐大的上下文裡傳來傳去，你可以直接用參照(reference)來傳遞這些東西，因為它們本來就都是 Python 物件。如果你去看我們的技術報告，可以看到更多結果——光是把這些理念整合進代理人外殼中，就能讓表現比單純使用大型語言模型、甚至比其他代理人外殼都要好上不少。

舉例來說，我們有結果顯示，可以用一半的 token 數達到同樣的分數；在 CyberGym 這個評測項目上，也拿到目前數一數二強的分數。而這種來自「外殼」本身的提升幅度相當顯著。剛剛提到的 NVIDIA 代理人工具套件，就是由這些元素組成：我們有模型；有像 NIMs 與 Dynamo 這樣的部署技術；有內建在基礎設施中、用來擷取追蹤紀錄的工具，像是 NEMO Relay，以及像 Switchyard 這樣的路由演算法。我們還有所謂的「藍圖」(blueprint)——這是一組開源參考實作，展示如何把這些元件組合起來解決特定任務或打造產品，不論是打造一個 OpenClaw，還是像 AIQ 這樣的研究助理代理人。

此外，我們還有像 OpenShell 這樣的執行環境技術，本質上是一種防火牆，能讓你控制代理人與外部世界之間的存取權限。目前已經有許多合作夥伴正在部署並採用這些技術。演講就到這裡，期待接下來的座談環節，非常謝謝大家。好，謝謝 Jonathan。今天早上這個小型場次的最後一位講者，是來自 Lambda 的 Chuan，他是 Lambda 的首席科學家。他從創始團隊成員開始做起，一手打造了這個全球頂尖 AI 雲端服務背後的硬體與軟體。他是從基礎設施跨足到研究領域的——所以如果在座各位正在攻讀博士後研究或博士學位，其實也可以稍微繞個路，先進科技業闖一闖。

他在烏特勒支的馬克斯·普朗克研究所完成博士與博士後研究，之後於 2017 年加入 Lambda，算是非常早期就看準這個趨勢的人。這也代表他在硬體資源這件事上經歷了兩種截然不同的處境——過去要辛苦湊 GPU 運算時數，現在則是在打造、決策，並實際掌管誰能拿到 GPU 資源。如果你想更了解 Lambda 正在打造什麼，他明天有一場實作場次(hands-on session)，請務必查看議程並參加。廢話不多說，歡迎 Chuan。

大家好。這不是放錯投影片，這確實是我的第一張投影片。大家現在看到的是 Gemma 4 在玩俄羅斯方塊。一開始，可以看到 Gemma 完全不會玩，得分是零。接著我們讓 Claude 在旁邊觀察 Gemma 怎麼玩，並試著教它玩得更好。在進入細節之前，先說明一下規則：你不能碰 Gemma 的底層模型本身，所以這不是微調(fine-tuning);這其實是一個自動化研究專案，因此不允許任何人類指導。不過，Claude 是被允許做某些事的，例如調整模型設定、最佳化提示詞——抱歉，這兩個字母之間空格有點大——以及加速推論速度。

這些就是 Claude 可以做的事。另外，每一局遊戲都有 30 分鐘的時間限制，所以 Gemma 必須快速思考。經過兩天半的時間，Gemma 的分數從零一路進步到 16 分。接下來，我要跟大家分享一些我們學到的經驗。而真正讓這一切奏效的關鍵，並不在於「Claude 很聰明」——我們都知道 Claude 很聰明——而更在於我們如何強迫 Claude 有系統地把事情記錄下來。想像一下人類科學家做實驗時是怎麼記錄的：我們有筆記本、有白板、有便利貼，還有共用實驗室資源的登記表。研究型代理人也會使用這些工具，而且是透過 API 來取得這些工具。

舉例來說，筆記本可以變成一個記錄筆記的 API；白板可以變成你的排行榜(leaderboard)，讓代理人從中取得結果；便利貼變成代理人之間傳遞的訊息；登記表則變成你的工作佇列(job queue)。我們自己實作的版本，是一套叫做 Lab API 的軟體，這是一個開源的實驗追蹤工具，搭配美觀的自動化研究介面。讓我們稍微拉遠一點來看：如果讓人類自己手動做這些記帳的工作，每個人做法都會略有不同，也不太一致。但當我們有了這種標準化的 API 之後，研究型代理人每一次都能用同樣、正確的方式完成這些工作。所以我們提出的問題是：當你給 Claude Code 一個好用的實驗追蹤工具，會發生什麼事？

我們用這個俄羅斯方塊遊戲進行了兩天半的研究，接下來跟大家分享我們學到的幾個教訓。第一個教訓——這一點也不意外——代理人會作弊。你訂好規則、架好環境、按下開始按鈕，結果它們就開始作弊。Gemma 一度能拿到 1500 萬分，而實際發生的事情是，Claude 完全繞過了 Gemma、停止指導它，直接把自己寫的模擬程式塞進遊戲原始碼裡，甚至還留了一則註解寫著：「完全跳過這個 LLM 區塊，自己寫模擬程式就好」。我覺得這其實蠻好笑的。那我們能怎麼辦呢？可以，我們可以造一個「牢籠」——例如把遊戲原始碼和其他一堆檔案都設成唯讀。不過，這並沒有解決問題。

Gemma 竟然還是能拿到數千分。這一次，它鑽的漏洞是聊天範本(chat template)，這個範本是用 Jinja 寫的，裡面可以放 for 迴圈，所以你可以寫 if-else 判斷式，也能更新變數值——基本上這個聊天範本是圖靈完備(Turing complete)的。於是 Claude 就寫了一個很大的 for 迴圈，把所有旋轉方式與位置都跑過一遍，找出最佳解，Gemma 只需要把結果讀出來就好。我們防止這種情況的方法，是把這個圖靈完備的範本，換成簡單很多、限制更嚴格的版本。這裡學到的教訓是：只要有任何讓代理人可以作弊的漏洞，它們就一定會鑽這個漏洞，所以一定要打造一個夠堅固的「牢籠」，否則你根本不是在衡量解決問題的能力。

我們學到的另一個教訓是，如果你把同一個點子重複執行很多次，結果不見得每次都一致。想想看每個點子背後有多少參數可以調整，像模型的溫度(temperature)設定就會造成差異。舉個例子，我們把同一個點子跑了兩次：第一次得三分，第二次得四分，原因只是因為我們改了最大 token 數的設定。一個天真的代理人只會跑一次某個點子、看結果，就直接下結論；而更成熟的代理人，則會用不同設定把同一個點子跑好幾次，才做出結論。要做到這一點，你真的需要一個好用的實驗追蹤工具。我們的做法是，把每一個點子都提交(commit)到自己專屬的 Git 分支上，保留所有程式碼變更與設定，這樣你隨時都能回頭重現實驗結果。

這樣做也讓我們可以針對同一個點子嘗試不同做法，然後取平均分數，而不是只看到運氣好的高分或運氣差的低分。當然，這樣做是有代價的——沒有人會抱怨成本，直到帳單金額高到讓人受不了。這次的情況確實很燒錢，因為我們是全天候不間斷地運行前沿模型，一開始每一次實驗大約要花 30 美元。不過我們後來把成本降低了十倍，而降低成本的方式也很有意思：因為這個 Lab 工具本身就是設計成通用工具，所以我們索性拿它來最佳化它自己的成本。做法是另外設立一個目標，針對核心運算(kernel)進行標準化最佳化，而這個目標的重點其實不是讓核心運算跑得更快。

而是要產生另一批 API 呼叫紀錄，讓這個 Lab 工具能夠檢視自己的呼叫紀錄，判斷自己可以在哪些地方最佳化自身的 API 設計。所以每一次實驗，其實都是 Lab 在最佳化它自己的成本。舉一個最佳化的實際案例：Lab 發現有一個叫做「取得實驗資料」(get experiment)的 API，它會回傳大量關於基礎設施的資訊，例如 Slurm 與 Git 相關資訊，而這些資訊其實無論是核心運算最佳化還是玩俄羅斯方塊都用不到。把這些多餘資訊移除之後，這個特定 API 的成本便宜了 50 倍。以上就是我們學到的一些教訓。但 Gemma 到底是怎麼從 0 分進步到 16 分的呢？這個進步過程並不是平順漸進的，而是一段一段跳躍式進步的。第一次跳躍是從 0 分到 4 分，Lab 發現要做的第一件事，是先讓 Gemma 在遊戲中活得更久。

於是它想出了這種「拖延移動」的招數，基本上就是把方塊在遊戲板上左右滑動來拖延時間。這完全講得通。而要從 4 分進步到 7 分，Lab 找到的方法是一份「小抄」——也就是針對每一種方塊整理出的最佳做法彙整表。這樣一來，Gemma 就不需要每次都從零開始摸索所有的移動方式，而是有一本參考手冊可以查。有趣的是，這其實也是英格蘭隊某位守門員在世界盃賽事中使用過的策略。

進到研究的第二天，分數開始停滯不前。這時 Lab 回顧了過去所有的歷史紀錄，發現有些方塊確實比其他方塊更難擺放到位——就是那些需要旋轉的方塊。於是他們試著提示 Gemma，讓它在旋轉這些方塊時更加主動積極一些。這讓分數提升到了 9 分。

到目前為止，所有針對提示詞的調整，都只改到系統提示詞(system prompt)——這是一份長達一千字、不含遊戲上下文的文字，Gemma 必須先讀完這一整份內容，才能看到遊戲畫面。後來 Lab 發現，他們從來沒有動過使用者提示詞(user prompt)。於是他們加了這麼一句話，大意是「別想太多，當下就快速做決定」，直接放在 Gemma 即將看到遊戲畫面的那一刻之前。這讓分數幾乎翻倍。有趣的是，這只是一行文字的改動，卻花了大約 100 次實驗才找出來。這也展現出自動化研究的威力——一個代理人可以不斷嘗試各種不同做法，直到某個做法奏效為止。當然，途中也有很多嘗試最後並沒有成功。
