在 Replit，我們每天都會為使用者產生數十萬台虛擬機器，而且完全是透明運作的。我們曾經遇到一個長尾問題：有時候虛擬機器完全開機所需的時間，會比代理人執行環境（agent harness）準備就緒還要久。由於代理人非常急於除錯問題，所以在少數發生這種情況的時候，我們的代理人就開始不斷嘗試各種方法，想搞清楚為什麼沒辦法執行程式碼、為什麼沒辦法執行某些工具。代理人本質上是非決定性的，這代表每一次的追蹤紀錄都不會顯示出同樣類型的錯誤，因為代理人會決定採用不同的除錯策略。但這些紀錄的共同點，都是虛擬機器開機不夠快。

如果只是靠人工分析日誌，我們絕對不會發現這個問題。舉例來說，這個問題也不會出現在我們自己或 Datadog 的儀表板上，因為這是個長尾錯誤。但在我們把所有資料聚類分析之後，我們發現這種情況其實發生得夠頻繁，於是我們的系統立刻自動產生了一個 PR，當場就把問題修好了。所以我今天想帶給大家的重點是：不要再把評估（evaluation）只當成上線前的最後一道檢查關卡，它不是一個告訴你「這個 PR 該不該上線」的布林值開關。你應該把評估當成一具引擎，幫助你每一天都能出貨一個更好的代理人。謝謝大家。

ALEX GRAVELEY——嗨，這樣可以嗎？好，太好了。我是 Alex Graveley，之前主導過 GitHub Copilot 跟 Perplexity 的 Computer 產品，最近剛創辦一間新公司叫做 Flying Object，專門研究我們今天要談的一些主題。今天的主題是「全知代理人」。傳統上，代理人一直受限於它們能看到、能存取到的東西，我們認為這也是為什麼一定需要有人類參與其中（human in the loop）。而我們想做到的，是讓人類能夠更少參與其中，或者可以把這個迴圈裡不同的部分外包給代理人去做。那該怎麼做到這件事？這就是今天要討論的內容。現今的代理人其實就是一堆基礎元件（primitives）的組合，如果你要從零開始打造一個代理人，基本上每一個元件都得自己實作出來。

你需要一個執行層，不管是在本地端執行，還是在沙盒（sandbox）裡執行都一樣，這個執行層要有一大堆指令，用來操作檔案、執行指令、執行 CLI。你還得微調一整套資產（asset）生成能力，可能是文件、網站；PR 也是我們正在努力讓這些代理人做好的另一種資產形式。為了做到這些，我們需要一些協調用的基礎元件（orchestration primitives），這些現在已經變得相當標準了。細節其實沒那麼重要，重要的是它們的功能。舉例來說，擁有一個和母代理人（parent）context 不同的子代理人（subagent）是很有用的；擁有一些技能（skills），可以補足模型權重本身無法表達出來的地方，也是很有用的。

擁有記憶（memory）能力，讓代理人可以從過去學習，也是很有用的；能夠排程任務（schedule tasks），處理需要重複執行或是要按排程執行的事情，也很有用。而現在我們有了迴圈（loop），這是一種以目標為導向的執行方式。所以我們原本有一個個獨立的任務，這些任務會壓縮合併成一個迴圈，而這個迴圈要一直執行到目標達成為止。然後還有即時資料（live data）這一整個範疇，你需要網頁搜尋、瀏覽器控制、電腦控制、MCP、API，這些全部都要。這就是現在代理人的樣貌。如果我們看這裡面的共通點，會發現你依然是在「控制」這些代理人，因為代理人其實並不真的知道該做什麼，它對下一步該做什麼的建議往往也不太好。

所以需要有人類參與其中來指揮代理人，這樣一來瓶頸就變成了你身為代理人工程師——或者說得更精確一點，代理人的使用工程師——的注意力。你要管理這些迴圈，同時平行執行一堆東西，有些進行得順利，有些出了問題，你大概能感覺得出來發生了什麼事，你可以喊停、可以分叉（fork）、可以重新啟動，諸如此類。但我們現在做這些事情的方式，其實跟大概一年前已經非常不一樣了。我們實際上正在往上爬這個複雜度的層級，代理人現在自我引導的方式，跟以前完全不同。我們一開始只是從工具（tools）起步。

我們信任代理人會呼叫正確的工具，接著我們開始信任代理人能自己做 commit，再來我們開始信任代理人能做出完整的 PR。而我們現在已經走到，信任代理人可以為了達成這種迴圈式的目標，一次做出多個 PR。我認為接下來再往上一個層次，會是「功能（features）」。功能可能涉及執行一個實驗、觀察即時資料、檢查異常狀況、檢查使用者情緒反應，把接觸到這個功能的使用者做區隔分組，看看它是否對你的核心目標——比如留存率或營收之類的——產生影響。再往上一層，我們就進入「專案（projects）」的範疇，也就是一整套功能的集合，用來滿足產品裡的某個需求。

而我認為最頂端，會是整個「產品（products）」。當你有一個自我引導的代理人時，你只要用很高層次的方式描述你想做出來的產品，它就能自己去把產品做出來、部署上線、反覆迭代、找出它需要哪些功能——這些功能也許在其他地方根本不存在——嘗試幾種不同的做法，然後用這種方式自我引導。那我們該怎麼支撐起這種不斷增加的複雜度跟範疇呢？因為每往上一個層級，都需要新一代的模型，或是複雜得多的代理人執行環境（agent harness）才能達成。所以我們認為，這裡面的共通點大概就是兩個軸，驅動範疇擴大的兩個軸，一個是洞察力（insight），一個是控制力（control）。

洞察力指的是代理人能存取到什麼樣的資料，以及以什麼形式存取，好讓它能從中導出洞見。抱歉，我時間到了。

而控制力則是代理人在這些資料與即時系統上進行操作的能力。所以我們現在做的事情，其實是從「看見程式碼」轉變成「看見整個事業（business）」。這樣一來，我們就能開始搞清楚真正的商業目標是什麼、應該存在哪些產品、或是為了達成這些目標應該存在哪些功能。現在這件事還是得靠人去想、去猜測，但我們想做到的，是讓 AI 也能做到這一點。同樣地，這個流程的一部分，也就是產品開發週期的一部分，包括執行實驗、部署變更、監控即時系統、視需要擴展這些系統的規模。所以這兩件事加在一起，就構成了代理人不斷擴大自身範疇的這兩個軸。

這裡面有一堆尚待解決的問題，例如處理大量資料。一般來說，你會希望能擷取並索引一個企業內部發生的所有事情，你會希望能把這些知識壓縮成代理人可以使用的形式，你會希望能有觸發機制（trigger）。如果你要同時執行大量的實驗，而且很可能沒有人類參與其中，你會希望代理人彼此之間能夠互相察覺、有效協調，還有其他一大堆問題。最難的一點是，有時候你根本不知道你要最佳化的目標函式是什麼。這些就是我們認為，要打造出未來這種自我引導代理人所要面對的尚待解決問題。對。

所以我們想做的，是把整個系統都圍起來、掌握一切。我們希望能把宏觀的脈絡（macro context）交給代理人，讓它們能在完整掌握狀況的前提下運作，並且提供正確的基礎元件，讓這些代理人能夠部署變更、監控這些變更、並依此擴展規模，以達成那些商業目標。在我們往上爬這個複雜度層級的過程中，這會是一段漸進的過程，但我認為這就是我們正在前進的方向。所以，如果大家想試用我們正在開發的早期版本，Flying Object 有候補名單可以登記。除此之外，我在 Twitter 上是 Alex Graveley，很樂意跟大家聊聊。太棒了，謝謝你，Alex。好，我們接下來要轉場進入一個座談環節，而且我們會用最快的速度進行。
