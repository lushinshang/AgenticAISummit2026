好，接下來這部分要談我之前做的一些工作。基本上重點是：模型本身並不是代理人（agent），或者說，三億個代理人軌跡（agent traces）教會我們關於模型與其執行框架（harness）的事。我叫 Zach Mueller，是 Lambda 的開發者關係主管。事情要從三月底說起，當時 Hugging Face 的執行長 Clem 發了一則推文，大意是說我們需要更多開放的軌跡資料集，因為這些模型非常聰明，尤其是那些我們沒辦法在家裡跑的大型模型。當時的想法是，如果把這些大型模型的軌跡拿來訓練小模型，小模型可能會表現得更好。於是我們就開始動手，看看結果會怎樣。

這個做法看起來相當簡單，對吧？先找一個前沿（frontier）、最好是開源的模型，這樣才不會有人陷入法律灰色地帶。從它身上產生一些推理軌跡，也就是推理過程、行動與結果，然後用這些軌跡去訓練一個較小的模型。接著就會碰到一個有趣的問題：重點其實不在模型本身，因為不管你用的是在 Claude Code 裡跑的 Opus，還是在 Codex 裡跑的 Kimi，都不重要，因為真正決定模型表現好壞的是執行框架（harness）本身。而這個答案往往不是那麼直觀。舉例來說，這是在 Terminal Bench 上的結果。大家發現，以 Gemini 3 Pro 為例，Google 官方為它做了一套 Gemini CLI 執行框架。

你可能會以為，在像寫程式這類特定的評測上，用模型當初訓練時搭配的那套執行框架，表現應該最好。但實際上，只要換成一套精簡、設計得當的執行框架，模型的表現不但提升了 8%，跑一次評測的成本還便宜了將近 20 美元。反過來看 GPT-5.5，OpenAI 自己訓練這些前沿模型，也有 Codex 這套框架，結果是 Codex 表現更好，好了 5%，但成本卻是四倍，因為 OpenAI 可能有誘因讓模型跑得更久、想得更多，把問題解決得更徹底，多拿到那 1% 的提升。這是個合理的工程考量。但這也意味著，你不應該永遠只死守一套執行框架。

你應該多方嘗試。再舉一個例子，KimiK3 上禮拜才剛推出，某個實驗室針對 26 個完全相同的任務，比較不同執行框架在表現、成本與時間上的差異，看看哪一套最好。不出所料，跟模型一起打造出來的那套框架表現最佳。Kimi Code 在 26 題中答對 21 題，成本 0.54 美元，耗時將近 300 秒。第二名是 Hermes Agent，這是 Nous Research 打造的開源執行框架，表現幾乎一樣好，成本更低，速度也快了將近兩分鐘。此外還有幾套其他的開源框架，像是 PyAgent 和 OpenCode，但我特別覺得有意思的是，Claude Code 也拿到大約 19 分，成本卻是其他框架的三倍。

這是因為 Claude Code 會在其執行框架裡塞進大量系統提示詞（system prompt）。所以很多人想拿最新的前沿模型去套用一套可能不太適合的執行框架，因為它大部分的上下文視窗（context window）其實都被這些系統提示詞占掉了。所以，這其實是一個需要判斷的問題：也許不是每套執行框架都適合每個模型，我們甚至可能不知道哪套框架最適合，但至少該去試試看。現在來談談所謂「軌跡」（trace）到底是什麼，先給它一個統一的定義。使用者會對模型下提示詞，比如說「幫我實作這個函式」或「幫我實作這個伺服器架構」，又或者如果你用的是 Codex，就是「幫我做一整晚的前沿研究，祝你好運」。

接下來代理人迴圈（agent loop）裡實際發生的事情是：它會先花一段時間推理，判斷下一步該怎麼做，接著呼叫一些工具，然後判斷是否已經成功完成提示詞交代的任務。如果還沒完成，就會一直重複這個過程，直到模型判定已經有解答了，或是需要人類介入為止。這件事之所以重要，是因為如果我們了解模型的行為模式，之後或許就能拿這些軌跡去訓練出一個總參數量更小、但表現更好的模型。這樣就可以在家裡的裝置上跑，例如單張 H100 之類的。問題是，我們得先決定要用哪一套執行框架，我們選了 Hermes Agent。

當時它才推出沒幾個月。我們跟 Nous Research 有不少良好的合作關係，而且我自己在家裡用的就是 Hermes Agent，而不是 OpenClaw，所以我個人對它也有些偏好。於是我們就選定了 Hermes Agent。這是第一步，對吧，我們先搞懂這個世界的樣貌，以及要怎麼跟它互動。第二步是決定 Lambda 要挑哪些模型來產生這些軌跡。基本上要符合三個條件。第一，授權必須夠寬鬆，因為我們不希望有人還得擔心這些軌跡能不能用在商業用途、興趣用途，甚至能不能放在自己電腦上。我們希望這些資料能自由地開放給大眾與社群，讓大家想怎麼用就怎麼用。

第二點是，我們希望鎖定那些一般人在家裡跑不動的模型。當時是三月，最先進的模型是 Kimi K2.5 和 GLM-5.1，分別是一兆參數與八千億參數。除非你剛好家裡擺了四千張或六千張 Blackwell 晶片，讓你的電費暴增，不然我猜大部分人根本沒辦法在家裡跑這些模型。除此之外，我也很關注模型本身的能力。當時 GLM 在程式撰寫方面是最先進的，但那也正好是 Kimi 剛推出、引入「Kimi swarm」這種模式的時期：在同一條推理鏈裡，可以同時獨立進行多條工具呼叫鏈，這對這些又小又快的模型來說非常有價值。

回顧一下，如果我們有平行工具呼叫（parallel tool calling），舉例來說，我們可以說「來，快速幫我建一個網頁服務」。很好，這時你的開源模型就可以同時動手，一邊開始搭建像是 FastAPI 路由的框架，一邊為它們寫單元測試，同時還能追蹤版本變化之類的，透過三條各自獨立的推理軌跡同時進行，而且你根本不需要三個不同的子代理人（sub-agent）來做這件事。至於我們實際上怎麼產生這個語料庫：我們讓 Kimi K2.5 想出大約 7000 個從基礎到具挑戰性不等的程式撰寫情境，範圍從電腦操作（computer use）到寫一個基本的 hello world py 檔案都有。

接著我們把這些提示詞全部丟進 Hermes Agent，後端換上不同的模型，也就是 Kimi 和 GLM，動用了 184 張 H100，跑了大約一週多。最後我們從每個模型各得到 1.5 億筆軌跡，這些軌跡會經過驗證，確認軌跡本身合理且成功，成功的歸到一個資料集；如果失敗但仍然有學習價值，就歸到另一個資料集。基本上，我們在完成後的那個週末就把它釋出，看看社群會怎麼反應，結果反應相當不錯。目前它在 Hugging Face 上大約有 380 個讚，每月下載量約 3000 次，第一個月釋出時甚至衝到大約 10000 次下載。但最有意思的是，我們觀察到一個趨勢：有人拿這些軌跡去訓練模型。Qopus 就是一個常見的模型名稱，基本上它是用 Opus 軌跡訓練出來的 Qwen 模型，於是就出現了這個 Qopus 模型。我們發現大家訓練的模型參數量範圍，從十億到 270 億都有，目的是打造一個能在家裡運作、表現優異的自主代理人，當你的助理，卻不需要花上幾千美元的硬體。

我們也觀察到有幾個特定陣營的模型被訓練出來。第一個是 Qopus，也就是 Qwen 3.6。特別的是，這些幾乎都不是混合專家（mixture of experts, MOE）架構的模型，因為大家普遍發現，當模型小到這個程度時，只要速度不是決定性因素——也就是說，你的代理人可以在家裡跑，你不在乎問題是 12 小時解完還是 2 小時解完，反正它就默默在背景做事——MOE 架構的優勢就沒那麼重要，反而不如用比較大、表現較好的模型。我們也看到一些有趣的實驗，有人特地拿 Kimi 的軌跡，試著把這種平行工具呼叫的能力，塞進像 Liquid 的 LFM 12 億參數這類極小的模型裡。有時候是成功的。

<!-- 轉錄不清 -->我還是認為，五十億到一百億參數大概是能做到這種較複雜工具呼叫能力的最低門檻。不過那仍然是很好的嘗試，另外還有一些專門針對 Hermes 訓練、設計來搭配這套執行框架運作的優秀模型。Harmonic Hermes 最終成為比較受歡迎的模型之一，跟 Qopus 一起，這兩個模型加起來下載量將近 50 萬次，而且到今天還在持續產生新模型。所以我希望大家從這場演講帶走的，不是「你一定要去蒸餾軌跡、訓練自己的模型」這種結論。我想挑戰大家的是：拿你喜愛的模型，以及你對平常使用的執行框架又愛又恨的那些怪癖，把這些模型硬塞進一個不同的執行框架裡，看看它會有什麼反應、表現如何。

它可能會展現出完全不同的個性，因為它身上沒有兩萬字的系統提示詞在引導它，模型可能會變得更有表現力；又或者你可能得稍微收斂一下，因為 Codex 本身就很強，需要被適當駕馭，而不是放任不管。但無論如何，我希望大家能帶走這樣的想法：如果我每天都用 Codex，那如果換成 Pi 會怎樣？如果換成 Hermes Agent 又會怎樣？多去玩玩看這個想法，開始拓寬視野，理解也許沒有一套執行框架永遠是最完美的，就算那套框架正是模型當初訓練所用的那一套。非常感謝大家。我們會留在這裡，有問題歡迎過來問。
