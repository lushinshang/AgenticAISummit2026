好，先從一個聽起來很理所當然、但之後會變得有點「昂貴」的概念開始。當你想到一般的 AI 聊天，它基本上是一個有邊界的任務：使用者送出一個提示（prompt），你得到給人類看的回應，讀完，就結束了。但到了代理型 AI（agentic AI），情況就不太一樣了，它不再有邊界。同樣是一個查詢丟進去，但代理（agent）會做規劃，可能會呼叫工具，看結果，可能不滿意，再呼叫一次工具，甚至可能啟動一整個代理群組的圖形工程迴圈去處理。現在同樣一件工作，可能只花幾秒鐘，也可能花上好幾個小時。這對我們來說意味著什麼樣的改變？

從外部視角來看，這代表當你在規劃產能，或是要幫團隊分配多少預算時，情況完全不一樣了。因為以前你基本上是用「席位」來規劃，把使用者分配給模型或服務。但現在，一個使用者可能只花幾秒鐘就得到回應，另一個使用者可能要花上好幾個小時，這兩種任務所需的運算量，等級完全不同。

這種轉變會打破幾件事情，我們這邊特別點出三個。第一是預算編列。我認為這也是我的副總裁把這點放進來的原因之一，因為我記得年初的時候，我們幫整個團隊編列了全年的運算預算，結果幾週內就用完了。這種情況在整個產業都在發生。兩個人用同一個服務，其中一個人的成本可能是另一個人的十倍、甚至一百倍，因為某個任務可能需要好幾個小時的代理迴圈運算。第二件事是，以前我們都很執著於 FLOPS 和每秒 token 數，還有 GPU 夠不夠快來處理這些任務，現在情況不太一樣了。

因為隨著多輪代理執行的普及，上下文（context）成長得非常快，現在要優化的是整個系統，因為現在有很大一部分是受限於記憶體頻寬。而就計分方式而言，以前我們執著的是每秒 token 數，但現在這個指標其實無法告訴你需要多少運算資源，因為重點在於「完成整個任務」，而不只是單一次回應。

所以我接下來要談的內容，其實都圍繞著同一個原則，簡單說就是「快取（caching）」。每一輪對話都會重複上一輪已經做過的工作。如果你想想上下文，在代理的迴圈裡，你在第十二輪執行時，基本上還是得重新計算前面十一輪已經做過的所有內容，才能再往前多算一點第十二輪的部分。但很明顯的答案是，為什麼不乾脆保留已經算過的結果，而要重新計算一次呢？這其實是過去幾年就已經被發現並實作的概念，只是現在做法變了。整個做法橫跨三個不同的層面：在模型層面做、在 GPU 堆疊層面做，也在 CPU 層面做。

這三個層面同時並行運作，確保我們不會撞上記憶體頻寬的問題。接下來用幾個快速的例子，說明我們跟 Moonshot AI 在 Kimi K3 上的合作是怎麼做到的。第一個是模型層面的角度。問題在於 KV 快取成長得非常快，每次得到新的回應，它就會不斷變大，對於超大型模型來說，這可能會非常龐大，甚至到達數百 GB。而你不可能把這些全部放進記憶體，尤其是 HBM，也就是 GPU 最快的記憶體。所以 Kimi K3，還有這幾年出現的其他模型，都試著在這方面做優化。Kimi K3 特別有趣的地方在於，他們在 93 層裡，有 69 層採用了一個全新的概念，叫做 KDA（Kimi Delta Attention），它基本上是用具有循環層（recurrent layers）的線性注意力機制（linear attention）。

所以實際上，這些層所需要計算的 token 數量是固定的。在我們用 AMD MI355 GPU 做的實驗中，一個節點有八張 GPU，每張有 288 GB，結果只用了大約 15.5 GB 的記憶體，這比原本小非常多，對我們的運算來說好非常多。

好，接下來是 GPU 服務堆疊。如果每個請求的快取都要存進 HBM 裡，你不可能打造出一個真正可行的資料中心。所以隨著 Moonshot 這個新模型，我們基本上重新設計了整個分層快取（tiered cache）架構。現在我們的架構是：最上層是 HBM，往下是 CPU 的 DRAM，然後是 SSD，再往下則是共享記憶體池。這些層級加在一起，就構成了這個分層架構。重點在於，當一個代理在執行任務時，它會執行任務、等待結果回來，不管是工具呼叫還是在 CPU 上完成的其他事情，中間都會有大量的閒置時間。

所以當快取被驅逐（eviction）發生時，你會希望確保 GPU 依然保持忙碌、持續被使用，因此有很多快取有時候會被驅逐掉。用我們現在這種分層方式來做，前綴（prefix）基本上早就準備好了，等模型準備好要執行任務時就能立刻用上。這也是為什麼我們把過去常見的第 99 百分位延遲，從舊方法的 17.3 秒，降到了 5.4 秒，也就是比之前快了 3.2 倍。

在 CPU 這邊，隨著代理型 AI 的發展，CPU 也變得重要許多，上面發生了大量的運算。這也是我們可以談談如何讓工具呼叫更有效率、CPU 執行更有效率的地方。一個很好的例子就是分詞（tokenization）的部分，這部分其實也可以快取。這是我們想呈現的另一個例子：如果你只快取新增的部分，你大概能得到一個穩定的 0.09 毫秒，相較於整個重新計算要花 1.7 秒。所以我們在 CPU 端也得到了很大的運算效率提升。

我們也想特別提一下這個部分，這對某些人來說可能聽起來有點反直覺：你算出來的工作量和數字改變的方式。很多人會回報快取命中率（hit rate），但你可以在這個例子裡看到，實際上快取命中率反而變低了——從 88.5% 降到了 87.5%。乍看之下你可能會覺得，哇，這樣更差了。但事實是，我們剛才提到的「首個 token 的時間」，之前提到快了 3.5 倍，而這才是我們現在真正在衡量的東西。重點在於「成功完成的執行」，因為那個 89.5% 的命中率，如果你還是得花很久才能算出第一個 token，其實意義不大，使用者體驗還是會拖得很長。

所以最終，使用者即使在快取命中率較低的情況下，體驗反而更好，這仍然是更好的體驗。但核心問題是，我們需要用「每次成功執行的成本與時間」來衡量，而不是像以前那樣只看每秒 token 數。這差不多是我們簡報第一部分的結論：贏家是那個能用最少成本完成最多任務的人。AMD 也正在朝這個不同的方向前進，接下來大家會看到更多這方面的發展。謝謝大家聽完這部分，我們接下來要快速切換到工作坊的投影片，我不確定大家有沒有拿到那張紙條？都有了嗎？好，接下來就是動手實作的部分了。

再重申一次主題：不需要的運算就不要算。另外也要專注在隱私、安全性和效率上。今天要談的內容有很多是關於路由（routing）。但一般來說，當我跟很多開發者提到路由時，大家第一個想到的通常是模型內部的路由，也就是 MOE（mixture of experts，混合專家）的概念。稍微講一點背景，路由這個概念，其中一篇著名論文來自 1991 年 Jeff Hinton 和他的團隊，當時就已經探討過這個想法了。但那是早期階段，當時的運算能力遠不如現在，模型也小得多。他們在 2017 年重新回到這個想法，並針對規模大很多的模型進行探討。

如果我沒記錯的話，他們用了一個超過一兆參數的模型，並且在這個過程中發現了更多東西，像是稀疏門控（sparse gating），以及如何透過他們的門控演算法做出更好的專家選擇。而這個方向一直持續發展，所以你會看到越來越多的 MOE 模型出現，這也是目前的技術前沿之一。

但同樣的路由概念，其實也可以套用在模型上。與其把「專家」當作路由的目標，你其實可以把「模型」當作路由的端點。這也是我們今天要講的內容：我們會有一個模型跑在像這樣的一台機器上，它其實就在資料中心裡，可能外型稍有不同，但運算能力類似。這台就是 AMD Ryzen AI Halo 主機，目前市面上就買得到，內建非常強大的 CPU，你可以在本機端跑模型，我們稍後會在投影片裡快速展示。這就是你等一下要用來跑本機模型的機器，同時你也會有一個雲端模型可用。這麼做的重點就是我這邊列出的三大支柱。

首先，你可以在成本上省下不少錢，因為不是每一個 token 都值得用最頂尖的前沿模型去處理。舉例來說，如果你只是要找個檔案或執行一個簡單指令，根本不需要把它送給你的 Frontier 模型。<!-- 轉錄不清 --> 就品質而言，你可以在需要的時候再升級，也可以用專門化的模型來處理那些用專門模型就能搞定的任務。最後是隱私與安全性：我電腦裡有很多個人檔案，我不太放心把這些送到雲端，我不希望我的社會安全碼出現在別人的訓練資料裡，所以把它留在本機處理可能是比較好的做法。

我們今天要談的「混合模型」這個概念並不是我們自己發明的，這在學術界已經有人探討過。舉例來說，2023 年有一篇論文叫 FrugalGPT，裡面提到可以用一個模型來判斷送到小模型的回應結果，如果對結果滿意就直接採用，否則就往上升級到雲端模型。這是被探討過的其中一個做法，他們證明這樣可以省下高達 99% 的總成本，同時得到和當時的 GPT-4 非常接近的結果。

這個想法後來又被進一步延伸探討。這是一篇來自柏克萊的論文，他們的想法是，與其先用某個模型，不如有一個路由器（router）自動決定要用哪個模型，也就是所謂的 Route Element。結果也顯示出非常有希望的成效，可以節省超過兩倍的成本。

接下來是語意路由（semantic routing）。今天我們要介紹的，是透過一個叫做 Lemonade 的 AMD 內部專案所實作的語意路由版本，這個功能已經內建在他們的系統裡，可以跑在像這樣的本機系統上。概念很簡單：你會有一個嵌入器（embedder），把送進來的請求做嵌入（embedding），然後根據產生出來的向量，依照你定義的規則，判斷這比較適合模型 A 還是模型 B，並用類似餘弦相似度（cosine similarity）的方式來判斷該用哪個模型。接下來快速介紹一下 OpenClaw。OpenClaw 其實是一個規模大很多的專案，如果你從沒聽過它，簡單說它今年稍早開始爆紅。

它目前被公認是最受歡迎的開源軟體之一，基本上就是一個代理型的執行環境（agentic runtime）。我相信創辦人也在這場會議現場，說不定我們待會可以見到他。不過就我們今天要做的內容而言，我們會用它最簡單的代理建立功能。我們已經幫大家建立好了幾個代理讓大家玩玩看，等一下你們就會看到，如何透過 OpenClaw 實際操作我剛才提到的那些路由技巧。有一件事想先讓大家知道：你建立的每一個代理，都有屬於自己的工作空間（workspace），這些工作空間裡有一堆 MD 檔案、設定檔可以使用。舉例來說，Sole MD 就是其中之一，還有 agents.md；另外還有 OpenClaw JSON，裡面是所有跟模型相關的設定，包括你要用哪些模型、擁有哪些權限。

我們接下來要建立——其實我們已經先幫大家建立好了。舉例來說，你等一下要用的 local brain 代理，是連到一個本機模型；cloud 這個代理，則是連到跑在雲端的 Kimi 模型；而 smart router 這個代理，就是我們今天在工作坊裡要親自動手建立的路由器。

我們會涵蓋四種不同的路由方式。第一種，我想只要用過 Claude Code 或任何一種程式編寫代理的人應該都知道，你可以直接輸入斜線指令 model 來切換模型，這是最簡單的方式。但接下來會逐漸變得複雜一點：你可以為每個模型設立專屬的代理，或者也可以做到自動路由，也就是由一個代理根據你定義的規則，判斷這個任務是否需要升級到更大的模型。接著是語意路由，我剛才簡單提過，這部分我們會用 Lemonade 來實現，由 Satya 為大家介紹。
