**Hadar Sharvit：** 我們提供了一些資料類別（data class），代表我們對特定預測所做的不同聚合方式：看整個需求區間（horizon）的平均值，也看特定的營收。營收就是價格乘以需求。我們稍早也談過一些不確定性的衡量方式，稍後會用到。談過分位數（quantile）之後，我們不只能評估不確定性，一旦掌握需求的資訊，還能觀察它的高階導數，藉此了解彈性（elasticity），了解營收極大值出現在哪裡。這些概念很簡單，但要真正理解市場動態並不容易。好，我們談了數學，也談了市場動態、市場模型的程式碼。接下來要進入「有限制條件下的最佳化」。同樣為了舉例，我們用一個很簡單的資料類別，裡面有價格限制、需求的上下限、還有「最大步數」，也就是在整個區間裡，連續的定價策略值不能超過某個門檻。我們還寫了一個很單純但很關鍵的私有函式（private function），之後在最佳化過程中會用它來套用限制條件。要提醒大家，我們的目標是做出一個能讓獎勵（reward）最大化的最佳化，這裡的獎勵本質上就是營收，做法是呼叫市場模型的前向傳播（forward pass），了解需求在整個區間上的分布會是什麼樣子。在這個範例裡，我們單純用 SciPy 的 minimize_scalar，套用限制條件，並提供一個輔助函式，幫我們模擬獎勵、模擬整個區間的營收。

這只是一個輔助函式，用來確保我們設想的最佳化方式真的如我們預期運作。這是一個範例，我想我們之前分享過類似的東西。這裡看到的是市場模型在區間內某個固定時間點所描繪出來的營收地形（revenue landscape），底部凸出來的水平線代表某個產品的一個硬性限制，以價格（Y 軸）表示。在這個例子裡，我們的意思是：如果這是營收地形，價格政策絕不能推薦低於 C 點的價格；如果原本的全域最大值出現在 A 點，那麼加入這個限制之後，我們就只能勉強在有限制的情況下，找到只能在局部最大值 B 點取得的最適政策。當然，實際的營收地形很少這麼漂亮，也很少是可微分的，這裡只是給大家一點直覺。

好，我們談了能力（capabilities），談了數學上的抽象，也談了怎麼用簡單的程式碼把它們寫出來。接下來我們想把它接進一個執行框架（harness）裡。這裡看到的是，我們認為一個 agent 可以怎麼使用這些能力的簡化版本，我們會示範用幾種不同的方式把這些能力注入進去，然後看 agent 怎麼使用它們。第一個想到的做法是：每一項能力，像是我們談過的市場動態預測、最佳化流程，都把它們包成工具（tool）。這只是其中一個例子，而且這次示範我們並沒有真的連線到 Claude，不過大家在這裡看到的是我們使用 Claude Agent SDK，功能上其實跟 Claude Code 很類似。

如果你平常有用 Claude Code，這部分你應該會覺得很好上手。我們針對市場動態預測，寫了一個很簡單的包裝（wrapper）。我希望大家看得清楚畫面上的內容，不過我還是會用口頭說明帶過去。這裡看到的是，「predict market dynamics」這個工具，本質上是一個工具，搭配類似 Pydantic 的結構做設定，所以輸入內容會先經過 agent 驗證，才會真正呼叫市場動態的預測，而這個預測是包在一個 capabilities.py 檔案裡，也就是我們之前談過的那些能力。我們回傳的是一個結構化的輸出，裡面帶有 context，把我們之前談過的市場動態輸出——像是分位數本身、彈性的理解等等——都揭露出來。

我們接著把我們每一項能力都各自包裝成一個對應的工具。下面畫面上（為了簡潔起見，我沒有把所有工具都放進去），看到的是 Claude SDK 怎麼把一個 MCP 伺服器抽象出來。這裡有資料能力工具（data capabilities tools），本質上就是「去這些儲存桶（bucket）跟 GCP 把相關資料抓出來」，我要再提醒大家一次，我們接下來要問 agent 一個問題：「這裡的價格合理嗎？」所以我們要提供它真實資料，我們有一個 MCP 工具可以幫 agent 抓到相關資料。我們還有所謂的 Fetcher Capabilities MCP，本質上是我們之前談過所有工具的一層很薄的包裝，也可以說是一個伺服器。

接下來大家會看到我怎麼把工具做特定的分群。畫面最下面是資料工具，讓模型、讓 agent 可以抓到市場的真實歷史資訊。再來是大型市場模型工具（large market model tools），本質上就是市場動態的預測、最佳化，還有一些跟評估相關的工具。好，有了這些工具之後，我們要定義一個結構，讓特定工具只能被特定的子代理（sub-agent）呼叫。這個範例裡大家可以看到——Claude SDK 把這件事抽象得很漂亮，有興趣的話可以自己深入研究——我們有兩個函式，一個是分析師工廠（analyst factory），一個是分析師的初始化器。

我們定義了三個指定的子代理，還有一個負責協調的 agent。這個協調者的角色是「營收經理」（revenue manager），它會有一個系統提示詞（system prompt），內容大概就是你會覺得一個手上有三個子代理可以調度的營收經理應該要有的樣子。每個子代理都有各自指定的能力：一個懂市場動態，一個懂怎麼提供定價政策，還有一個 QA 分析師負責確認預測跟政策是否合理。這就是它被定義出來的方式，而且這是完全可以直接執行的程式碼。好，最後一件事，這比較偏向後設分析（meta analysis）。因為我們用的是特定的能力，我們想確保能把它們掛上鉤子（hook），把我們在意的資訊用可自訂的方式記錄下來。

通常當你觸發一個工具時，會有一個「post tool use」事件被呼叫，Claude SDK 有一個特定的 hook matcher，可以讓你在這個範例中，抓取某些功能——也就是工具被呼叫之後，你想要攔截那個時機點，做一些自訂行為。在這個自訂行為裡，我們想定義所謂的「grounding（扎根）」：我們想知道 agent 在推理過程中，是不是真的有在用我們定義的那些工具。這只是我想補充讓內容更完整的部分。說到底，Claude Agent Options 會把我剛剛講的所有東西整合起來：有給協調者用的總體營收經理提示詞（也就是系統提示詞）。

我們有所有允許使用的工具、MCP 伺服器、子代理，還有我剛剛定義的那些 hook，然後就讓這個 agent 開始執行。這是一個很簡單的查詢迴圈，純粹用來記錄跟印出過程中的結果。大致上就是這樣。好，我們談了能力，也就是真正用 Python 寫出來的能力，也談了怎麼把它們接到一個執行框架裡，接下來我們想跑一個實驗。在接下來的實驗裡，會讓兩個 agent 回答同一個問題。其中一個是 Claude Agent，本質上就是一個 Claude Code 的執行框架，它有推理能力、有網路存取，可以自己寫程式、自己執行，基本上它想做什麼都可以。

另一邊，則是 Fetcher，也就是有市場模型的 agent，它擁有能理解市場的那些能力，除此之外基本上跟前者一樣。我們會問它們同一個簡單問題：現在的價格合理嗎？這裡看到的是我們某位客戶真實（當然已經匿名化）的資料。大家可以看到，用逐年比較的方式，某個特定產品在特定市場的需求下降了 22%，而同一個產品的價格卻上漲了超過 60%，我們想把這個情境提供給兩個 agent，問它們：「這樣合理嗎？」答案並不是那麼直觀，有人可能會說「合理，因為我們看到的就是價格上漲導致需求下降」，但這可能不是正確答案，需求下降也可能是因為發生了別的事情。好，這是資料，也是輸出，我們剛剛談過我們有掛鉤去記錄每一次工具呼叫。畫面上方看到的，是那個什麼都沒裝的普通 agent 的目錄結構，下方則是有這些能力的 agent。兩者都各自產出了一些 markdown 檔案，記錄它們的思考過程，但最終兩邊都給出了一份建議的 CSV：價格要漲多少、要跌多少，接下來我們會看它們的差異在哪。

在講到這之前，大家可能已經開始有點直覺了——如果要你猜這兩個 agent 的建議會不會一樣。我想先帶大家看一下後設分析，看看這兩個 agent 實際上做了什麼。它們都很努力在做事：Claude Agent 寫了一些 Python 程式，讀了一些統計資料，用了它最愛的工具 Pandas，產出了一些 CSV，幫助它了解那個特定產品、特定市場的歷史資料、模式跟相關性，做了不少事情。另一邊，市場模型 agent 因為擁有那些能力，就大量使用了這些能力，而且不只如此，它還把使用這些工具背後（也就是那些能力）所得到的結果做彙整：解析結果、在上面建立產品清單、彙整最佳化的結果，乍看之下它用的工具數量遠遠更多。

如果我們把每個分析師呼叫工具的次數分群來看——我們談過我們有四個 agent，其中三個是分析師，另一個負責協調三者的是營收經理——我們發現一件很有意思的事：Fetcher，也就是擁有這些能力的 agent，在預測需求走勢的過程中，發現其中一項產品的預測存在一定的不確定性，可能是因為歷史資料不夠充分，但無論如何，這是 QA 分析師的功勞，它用「evaluate forecast」這個工具標記出，某個市場、某個產品的預測有很高的不確定性，並把這件事回報給它的上級——營收經理，營收經理接著把定價分析師重新派去處理那個子市場，於是大家可以看到工具呼叫次數出現一個尖峰，它們就這樣互相溝通、標記疑慮、回頭檢視能力，一路跑完整個流程。最後，在一個有六項產品的市場裡，Fetcher 分析師只建議了五個價格，也就是五筆定價建議，其中一個它判斷有不確定性的市場，它把這件事標記給了營收經理，這也成了理由說明文件（rationale markdown）跟建議內容的一部分。而那個沒有這些能力的普通 agent，當然是六個全部都給了建議，因為它完全沒有機制可以評估市場中的不確定性。

好，讓我們聚焦看其中一個產品，畫面上方單純是把建議的 CSV 內容印出來看，上面是普通 agent，下面是有能力的 Fetcher agent。針對某個特定產品，當下的價格是 1,100 美元，普通 agent 建議漲價 200 美元，而 Fetcher agent 則建議降價大約 250 美元。所以它們用的是完全一樣的資料，卻有不同的推理過程，得出的結論無論在幅度還是方向上都完全相反。我們來看看它們的思考過程。畫面上看到的是營收跟需求的估計，白色的點就是這個產品目前 1,100 美元的位置。我們先看 Fetcher agent 理解到了什麼：Fetcher agent 呼叫了市場模型之後，發現在這個價格點上，彈性的絕對值大於一，因此它建議降價，而且它發現在沒有限制條件的情況下，價格應該降到 828 美元附近，那裡正是彈性取得最大值的地方。

順帶一提，彈性就是價格變動百分之幾，會造成需求變動百分之幾。這裡引用一下 Rationale（理由說明）右邊的內容——這是 agent 其中一份輸出資料的原文：「在這條路線上，需求彈性很高，每降價 1%，訂位大約會增加 1.4%，足以彌補價格下降對營收造成的影響，甚至更多。」也就是說，它是根據我們提供的工具，理解市場接下來會怎麼演變，才做出這個分析，並據此建議調整價格。最後，營收經理 agent 用了這個結果，呼叫了定價最佳化工具，發現因為有限制條件，而且要顧到整個出發日期的區間，沒辦法真正達到營收最大化的那個價格點，但它最終決定選一個離那個點不遠的價格：863 美元。在理由說明裡，它也指出那個出發日剛好碰上假期，並用這點來說明：如果把這個市場裡各個價格對應的需求平均起來看，某些日期因為假期需求可能反而更高，這樣一來，反而可以把價格訂得更高一些。最後它跟市場模型一樣，落在 863 美元附近，營收經理對這個結果相當滿意，為了簡化，把數字四捨五入，最終出的建議價格是 850 美元。以估計來看，這讓那個特定產品的營收提升了超過 6%。至於那個沒有能力的普通 agent，它已經很努力了，真的很努力，但過程中它把相關性誤認成因果關係，它針對一些其實彼此不必然相關的市場做了相關性分析，我再引用它的原文一次：「在他調查的某個特定日期區間裡，需求彈性可以忽略不計，相關性接近零。」

所以（它認為）調高價格下限，幾乎不會帶來需求破壞的風險。本質上，它錯誤地判斷成沒有相關性。它犯的錯誤是，把原本不該放在一起比較的產品拿來做相關性分析。它從來沒有真正固定住某一個產品、只改變它的價格去做反事實（counterfactual）分析，因此才會誤判：可以調高價格而不會讓需求下降。但很不幸的是，彈性是真實存在的。到最後，在一個無偏誤的營收估計裡，這個做法造成的結果，接近負 8% 的營收變化，也就是營收不升反降。好，這就是我們今天看到的內容，讓我們把整個流程從頭到尾串起來，做個總結。我們談了一個通用的執行框架（harness）：我們定義了一個經理，負責跑迴圈、審核結果，彙整它找到的一切。我們也談了各有專長的子代理：它們把工作拆開來做，各自擁有自己的工具，彼此不共用 context，也不會被相似的工具搞混。它們有一個無偏誤的 QA 機制，可以檢查其他子代理產出的內容，而且最重要的是，它們全都使用了量化的能力（quantitative capabilities）。

數學就是在這裡發生的，公式就是在這裡被實作出來的，這也是營收經理 agent 知道自己不是專家、選擇把工作交辦出去的地方，這樣才能得到有意義又可靠的答案。當然，透過扎根（grounding）去觀察過程中實際發生了什麼，它才能提出和一個沒有這些能力的普通 agent 相比、明顯不一樣的建議。所以如果要我留一件事給大家帶走，那就是：把大型語言模型的協調能力，跟 agentic 執行框架的開發能力結合在一起，威力非常強大，但關鍵在於，你要知道什麼時候、怎麼把工作交辦給真正值得信賴、可以依靠結果的能力。所以，當大型語言模型負責協調的時候，真正涵蓋我們在 Fetcher 開發的所有智慧、並提供保證的，其實是這些能力本身。非常謝謝大家，非常謝謝。
