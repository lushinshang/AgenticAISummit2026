這個專案的目標其實很單純：降低代理人評估所需的工作量。我們歸納出三個主要挑戰。第一個挑戰是缺乏標準化。代理人並不像大型語言模型 API 那樣有共通的介面可以呼叫，代理人系統通常有各自不同的介面、工具、環境與執行方式，因此要在一個新的基準測試上執行代理人，通常需要針對該基準測試做專門的工程開發。結果就是，學習如何使用一個基準測試，往往有很陡的學習曲線。第二個挑戰是開放性有限，對於私有的代理人與模型，存取權限往往受到限制。第三個挑戰是可重現性低。這些問題加在一起，讓代理人評估很難重現，也很難規模化。

我們也在既有的基準測試設計中，發現了幾個限制。其中一個重要的限制是，許多基準測試是圍繞著大型語言模型本身設計的，而不是圍繞代理人本身。在許多情況下，基準測試允許使用者替換語言模型，但無法替換整個代理人的執行框架（harness）。這個 harness 包含了提示詞、工具、記憶、工作流程，以及圍繞模型的控制邏輯。當研究人員想用不同的 harness 評估不同的代理人時，通常需要修改基準測試的程式碼，這就造成了很高的整合成本，也可能導致測試系統與實際生產環境所使用的系統不一致。投影片上的例子來自 OpenHands 的程式碼庫。

這個程式庫裡有一個專門的資料夾，存放針對特定基準測試的調整程式碼，也就是說每個基準測試都需要自己的一套整合程式碼。現在想像一下，如果我們有 N 個基準測試和 N 個代理人，直接整合最多可能需要 N 乘以 N 這麼多份各自獨立的整合工作，這對大規模評估來說並不實際。為了解決這個問題，我們團隊有人提出了一個新的典範，叫做「代理化的代理人評估」（agentified agents assessment），簡稱 triple A。核心想法是把基準測試本身也轉換成代理人。這樣一來，就不需要把每個基準測試和每個代理人直接兩兩整合，而是雙方都透過標準協定來整合。我們在整個評估過程中，使用了像 A2A 和 MCP 這樣的既有協定，並且另外引入了一個評估控制協定。

這個協定定義了一套統一的評估工作流程，有助於讓整個評估過程更一致、更可重現。這個新典範帶來了幾個好處。舉例來說，它可以把基準測試和被評估的代理人分開，任何遵循所需協定的代理人都可以和基準測試互動；同時也減少了針對特定基準測試的整合工作量；此外，由於代理人本來就使用 A2A 通訊，支援多代理人評估也變得更加自然。這個整體工作流程給了我們一個概念框架，然而實作上仍是一大挑戰，有許多系統層級的問題可能會阻礙採用，包括部署、通訊、存取控制、可重現性，以及結果造假等問題。

為了解決這些問題，我們開發了 AgentBeats，這是一個開放的代理人評估平台。AgentBeats 簡化了整個評估流程，支援基準測試的開發、代理人評估、協作，以及結果追蹤。評估完成後，使用者可以透過排行榜分析結果，再運用這些洞見來改善自己的代理人設計。AgentBeats 支援多種評估情境，包括單一代理人評估，以及各種多代理人情境；它也設計了多種操作模式，這些模式支援不同的使用情境，以及不同的隱私或資料限制。我們也和相關系統做了比較，AgentBeats 的目標是在系統複雜度與整合成本之間，取得一個實用的平衡點。

代理人真的能在真實世界中完成具有經濟價值的工作嗎？ALE（Agent's Last Exam）讓這件事在專業工作流程的層次上變得可測試。今天我會談三件事：這個基準測試應該衡量什麼、如何把專家的工作流程轉換成可規模化、可靠的評估，以及目前的結果，能夠說明、以及還無法說明代理人準備好了沒有。

大家都知道，基準測試的作用不只是記錄進展。如果基準測試是可驗證的、被廣泛使用的，它就能為整個領域提供一個共同的目標，讓系統可以互相比較、讓失敗變得可見，也讓迭代速度加快。這些曲線圖在數學、程式設計、推理等領域都展現出同樣的模式，也說明了為什麼基準測試的設計如此重要，因為我們最佳化的，正是我們能夠衡量的東西。問題是，代理人的基準測試，衡量的究竟是不是我們真正希望代理人去做的工作。Anthropic 的執行長曾說，AI 會在 2027 年後不久，在幾乎所有工作上超越幾乎所有人類。不論我們是否相信這個時間表，大家的預期確實已經轉變了：代理人愈來愈常被討論成專業工作的助手，而不只是問答系統。

這也提高了評估的門檻。一個好的基準測試，應該要測試完整的工作流程，以及最終產出成果的品質。這張圖顯示了一種覆蓋範圍上的落差：代理人的基準測試，大多集中在程式設計與數學相關領域，而這些領域只佔美國就業人口的 7%。這個窄小的缺口其實非常巨大，在管理、金融、法律、工程等許多工作流程，測試都還遠遠不足。

這是一個標準循環：當一個基準測試發布之後，人們會如何針對它做最佳化。首先，你會得到一個基準測試分數，訓練團隊就會去向不同的資料公司購買訓練資料，希望藉此提升分數。接著你改善代理人的行為，再衡量進展。這就是一個基準測試如何影響整個產業的標準循環。

那麼，一個代理人的基準測試，究竟應該衡量什麼？

為了回答覆蓋範圍的問題，ALE 從一份外部的工作地圖出發。2018 年美國標準職業分類（SOC）涵蓋了整個經濟體中 867 個細分職業。下一步是利用 O*NET 在這份地圖中找出以電腦為中心的工作流程，ALE 篩選了大約 1,000 個 O*NET 條目中的數位化工作流程，把不同的職業變體整合成 100 個以 SOC 為基礎的代碼，再把這些代碼分成 55 個領域，並讓專家檢視邊界模糊的案例。我們以一個製造業的工作流程作為例子：製造業的標準流程，通常是先有一份 2D 藍圖，然後把這份 2D 藍圖在 SolidWorks 裡轉換成 3D 物件。第二張圖是以 iPhone 外殼為例。

你可以看到，如果模擬 iPhone 外殼的製造過程，會模擬塑膠熔化時的熱能變化，最終完成製作，這是第二個工作流程。第三個工作流程，則是如何把一塊塑膠方塊切削成型，最終做出 iPhone 外殼的形狀。這只是製造業裡三個標準流程的例子，這個基準測試裡其實還有非常多真實的工作流程。那麼，是什麼讓 ALE 與眾不同呢？首先，它的範圍非常真實，有超過 300 位業界從業人員參與貢獻。這篇論文所描述的首發版本，涵蓋了 55 個領域，共 760 個工作流程、1,500 個任務事例。

第二，我們不在乎你是用命令列介面（CLI）還是圖形使用者介面（GUI）來完成任務，我們只在乎最終的結果，只以此作為衡量依據。我認為這是第一個同時考量 GUI 與 CLI 的基準測試，盡可能模擬真實的人類工作環境。第三，是持久且以里程碑為基礎的評估：輸出結果與必要的中間狀態，會對照隱藏的參考答案或評分標準來檢核，因此對大型語言模型本身作為評判者的依賴非常低。綜合以上這些條件，改變了整個評估的目標。首先，先前的基準測試所發布的類別，對應到 ALE 的 55 個領域分類體系之後，可以看到它們涵蓋的範圍其實只有寥寥幾項。

第二，ALE 評估的是通才型代理人，能在同一個工作流程中，同時結合 GUI、CLI 或 API 操作。第三，衡量的單位是一項專業產出，是需要數小時到數週專家工作量的成果，而不是一個孤立的短暫操作。就 ALE 本身而言，最難層級（last exam tier）提供了基準測試內部最直接的證據：目前觀察到的最高完全通過率是 2.6%。這些主張都仰賴真實可信的任務與可信賴的評分。接下來我會展示，專家的工作是如何轉化成一套可執行的評估。另外，ALE 也已被最近 OpenAI 發布的 GPT-5.6，採用作為衡量能力與估計成本的頭條基準測試之一。建置 ALE 最困難的地方，不只是收集提示詞而已。

真正困難的，是在不失去真實性與可評估性的前提下，把專業意圖轉換成一個基準測試介面。所以 ALE 從最堅實的錨點出發，也就是專家已經完成的實際工作，一份完整完成的工作，本身就是真實性的有力來源。在我們外部投稿的流程中，專家會從自己過去的專案出發，而不是用合成方式虛構出來的提示詞，這樣才能保留真實的輸入、工具、限制條件，以及可供評估的可交付成果。但真實的來源不代表可以原封不動地拿一份保密工作照樣使用，作為基準測試，我們仍必須移除並替換掉一些敏感細節。

形式化驗證，利用正式驗證的方式，為這個問題提供了一個解決方案。除了產生程式碼之外，還要求代理人證明這段程式碼，在任何輸入下，都滿足一份形式化的規格，而這樣的證明，會由像 Lean 這樣的確定性驗證器來檢查，如此一來，正確性就是被證明出來的，而不只是被假設出來的。形式化驗證與大型語言模型之間有很強的協同效應，因為雙方各自解決了對方的瓶頸：一方面，形式化驗證為大型語言模型提供了它們所缺少的保證；另一方面，大型語言模型也為形式化驗證，帶來了前所未有的規模化能力。傳統上，形式化驗證需要深厚的專業知識，也非常耗時，但代理人可以將驗證任務自動化，因此能把這種保證，規模化地擴展到一般的軟體上。為了衡量這方面的進展，並提供改進的方向，我們建立了兩個基準測試：第一個是 Verina，衡量可驗證程式碼生成中的基礎能力；第二個是 Vero，衡量在真實世界程式碼庫下的端到端情境。在 Verina 中，我們衡量的是基礎能力。

具體來說，我們衡量模型在產生程式碼、規格、證明這三個基礎元件上的表現有多好。我們提供了 189 個獨立任務，來源是簡單難度的競賽風格程式設計題目。Verina 也支援衡量任務的組合，讓它成為一個靈活的基準測試，可以用來診斷模型在形式化驗證上的表現。它大約在一年前發布，當時最強的模型 OpenAI o3，也只解出了 4.9% 的證明任務。但隨著代理人與 agentic prover 的快速發展，加上模型本身的進步，目前最強的證明器，已經能解決全部的證明任務。所以在 Verina 之後，很自然會問的問題是：在孤立函式與獨立任務上的成功，是否能遷移到真實的軟體上？

這就是為什麼我們建立了 Vero，一個以真實世界程式碼庫為基礎、儲存庫層級的可驗證程式碼生成基準測試，來源涵蓋像是 Python、Rust、Dafny 等語言撰寫的真實儲存庫。我們手動建立了 43 個儲存庫，總共包含大約 700 項實作義務，以及 2,700 項形式化規格。為了確保基準測試的品質，每個儲存庫都經過一套非常嚴謹的整理流程，我們也人工檢查了所有規格。Vero 支援兩種評估模式：在「純證明」模式下，會提供儲存庫的參考實作，代理人必須證明儲存庫中的每一項規格都是正確的；在「程式碼加證明」模式下，代理人還必須實作每一個 API，並證明自己的實作是正確的。

我們也導入了一套形式化稽核機制，讓代理人可以透過提交形式化證據，持續改進這個基準測試。

在 Vero 中，我們關心的是一個儲存庫是否被完整證明，而不是只關注個別的規格。這是因為，否則代理人可能會提供退化的實作，或只解決簡單的規格、放著困難的規格不管。在這次評估中，表現最強的代理人是 Codex 搭配 GPT-5.5，也只能解出 27 個儲存庫，而在某些儲存庫中，代理人甚至連一項規格都無法證明成功。這使得 Vero 成為一個能抵抗前沿模型的基準測試。透過檢視評估結果與代理人的執行軌跡，我們觀察到，雖然目前的代理人已經能夠處理局部的證明義務，但要對整個儲存庫的全域不變量進行形式化推理，對它們來說仍然非常困難。
