套管（casing）是包覆在油井周圍的鋼管。設計這些套管的流程往往要花上好幾週，工程師得跑數百次模擬，還要參照許多埋藏在 PDF 與資料庫裡的標準。所以，我們設計這個代理人的做法有兩個關鍵部分。第一是確定性核心（deterministic core），工程師仍主導一切，使用可信賴的物理模擬器執行所有模擬；這些結果會依公司標準做確定性檢核，最終由工程師審核並核准安全設計的油井。第二是套管設計代理人，它全程跟著工程師，從數百次模擬中擷取所有正確的脈絡資訊。

這一切都根植於代理人的互動歷程。工程師可以提出問題，這些問題全部由代理人以類別層級的引用（class-level citations）來回答。最後，代理人會撰寫出油井設計文件，也就是所謂的「設計依據」（basis of design）。值得一提的是，這個代理人從不自行計算任何數字，也不驅動任何工作流程；因此，就設計而言，數值準確度是百分之百。所以，評估工作就歸結為：套管代理人回答工程師問題的表現如何，以及能否產出完整且正確的設計依據文件。為了評估我們代理人的表現，我們套用同一套四層評估框架：L0 是每年由領域專家（SME）簽核通過的設計依據文件數量；L1 是代理人設計與回答的文件是否完整、正確、且達到可審核（review-ready）的標準。

L2 聚焦在檢索與脈絡管理；L3 則圍繞在術語、根據性（grounding）、準確度與召回率。所以，我們與領域專家一起建立評估項目，並校準評分者。領域專家往往時間有限，所以我們以合成方式擴充他們的範本，再請他們驗證額外產生的資料。我們針對 L1 正確性做持續攀升式改善（hill-climb），把術語精確度從 83% 提升到 100%，論述精確度從 68% 提升到 90%。這贏得了客戶端工程師，也就是油井設計工程師的信任。我們現在正處於有限量產推行階段，會持續蒐集額外的正式環境軌跡、加以評分、演進評估集——這必須是持續演化的資產——並在此基礎上持續改進代理人。

值得一提的是，我認為評估集是持續演化的資產，是最持久的資產。你隨時可以更換模型，或調整代理人設計的各個面向，再拿這套評估集去測試。這其實就是我們客戶投資的智慧財產核心，也是幫助他們跟上、甚至站在基礎模型持續進步浪頭上的關鍵。再舉一個例子，這是我們與一家頂尖四大專業服務暨會計事務所合作的案例。我們在這裡建置了一個財務盡職調查（due diligence）代理人，協助分析師更快得到經過人工驗證的洞見，把原本要花四到六週的工作，縮短到兩天。同樣地，這也是用同一套評估框架。我們把 L0 定義為「得到人工驗證洞見所需的總時間」。

我們建立了完整的各層評估，並改進了 L1 正確性，持續攀升式改善並提升了 L1 正確性。這個案例同樣正在進行量產推行，我們從每一次執行中學習。而且，往往評估資料是否充足，是最大的瓶頸之一。所以，這些有限量產推行正是蒐集額外資料、演進評估集的絕佳機會。因此，對每一個大規模建置的代理人，我們都會召開評估設計審查會議。我們有一支前線部署工程團隊，與所有企業客戶以及政府機關合作建置這些代理人。這是我們用來當作每個代理人評估計分卡的效能成熟度矩陣，計分卡沒有全部綠燈，我們就不會上線。

最後，總結幾個關鍵原則。第一，你評估的是整個系統，不只是模型。第二，使用混合式評分者：能用確定性方法就儘量用，必要時才用模型評分，高風險場景與需要校準的情況則交由人工審查。第三，把評估集當成持續演化的資產，隨時間逐步壯大它，這是屬於你的資產。評估優先，正是讓「大致正確」蛻變為「可上線」的關鍵。如果各位也在做這方面的工作，我很樂意交流，我的信箱列在上面，謝謝大家。謝謝大家。好的，接下來換 Srijith 上場。大家午安，我是 Srijith Rajamohan，直到最近我都是 Redis 的 AI 研究主管，今天我想聊聊我們建置的診斷與修復代理人，這個代理人是用來診斷 Redis 查詢引擎相關問題的。

我們建置這個代理人，主要是為了協助客服人員處理大量的客戶查詢。Redis 確實提供了相當豐富的工具套件，以及相當完整的文件來因應這些問題。但我們真正注意到的是，到頭來，很多複雜查詢最後都會一路升級到開發團隊手上，這顯然不是理想的做法。所以我們建置這個代理人，就是想看看能不能疏通其中許多案例，縮短客戶得到解決方案的時間。特別具有挑戰性的一點是，跟 SQL 這類東西不同，LLM 內建的參數化知識相當有限，我們發現它常常會答錯。而且，這些查詢有些本質上就高度依賴脈絡，代理人必須知道一個查詢實際上缺了什麼資訊。

所以我們必須打造一整套具備技能與工具的代理人，讓它走過「釐清、診斷、確認」這個循環，才能讓整體更可靠。在這個過程中，我們學到了幾件事：只評估最終結果往往是不夠的，你怎麼走到那個結果、也就是軌跡（trajectory），也非常重要。而且，正確性固然重要，一致性同樣重要。我常說，比一套系統完全不能用更糟的，是一套「偶爾能用」的系統。這正是我們極力想避免的狀況。最後，沒有效率的軌跡顯然代價高昂。我們吃過的一個教訓是，這些低效軌跡下游也非常容易出錯，因為長度過長或脈絡窗口被耗盡。

當然，改用更前沿或更強大的模型，可以解決一部分問題。但真正對我們有實質幫助的，其實是重新架構這些知識，以及代理人存取資訊的方式。也就是說，我們要確保提供足夠的資訊，讓它知道如何辨識並取用資訊，以及該在什麼時候使用這些資訊。

我想特別指出幾點，這些是我們在建置這些代理人時觀察到的一些失效模式，大致可以分成四類。前三類——正確性、完整性與有用性——與最終結果有關；效率則與軌跡有關。正確性很直觀，如果結果是錯的，那當然是問題，成因可能有很多，例如路徑錯誤、讀錯指標等等，這些基本上都是幻覺（hallucination）。完整性，是指代理人只診斷出問題的一部分，其餘部分沒有解決，這是我們相當常見到的問題。

有用性其實可以分成兩類。第一類是代理人給出大量資訊，甚至是過多資訊，或是非常籠統的資訊，多到使用者根本無從採取行動，只是被資訊淹沒。第二類我們覺得相當有意思，是代理人提供的資訊或建議在語意上違背了使用者的真正意圖。舉例來說，當使用者問「為什麼我的查詢這麼慢」，代理人回答「減少搜尋詞的數量」，這技術上沒錯，但根本沒有真正解決問題。最後一類與效率有關，也就是代理人重複讀取、來回折返，或做了死路搜尋，因而浪費了大量的權杖（token）。

而且，如同我先前提到的，我們也注意到這些狀況同時會對準確度造成負面影響。而這些問題大多只有透過檢視軌跡才能發現，它們不會顯現在最終結果裡。所以我們從兩個面向著手處理。第一個面向是，我們能不能檢視工具架構，並在那裡做些調整？我們實際上做了兩件事：首先，能不能把工具拆成兩類——設定工具（setup tools）與自由裁量工具（discretionary tools）？設定工具在啟動時一律會被呼叫，而自由裁量工具顧名思義，則是由模型依據當下要解決的問題來決定是否呼叫。

換個角度想，這就好比你到一份新工作報到，通常會經歷一段新人訓練（onboarding）流程，有人會告訴你這裡在做什麼、誰負責什麼、該找誰談。我們可以用同樣的方式來理解：設定工具為代理人提供足夠的脈絡，讓它知道該如何正確往下走，也知道如何正確使用自由裁量工具，並知道什麼時候該用。第二點，是我們如何重新組織知識庫。當然，你可以直接使用原始文件，但我們發現，把知識重新整理成我們稱為「診斷手冊」（diagnostic playbook）的形式後，效能會更好。這其實就是一個路由器加上一組操作手冊：你可以把路由器想成——我在這裡展示了一個小結構或片段——你有症狀，每個症狀對應到一種問題類型，再路由到對應的一本或多本手冊。

使用者來找你的時候，不會直接說「我有某種症狀」，他們說的是自己的困擾。代理人的工作，就是把這個困擾對應到某個症狀或一組症狀。而我們的工作，則是讓代理人更容易完成這件事，這也是診斷手冊存在的目的。為了理解這些介入措施各自的效果，我們把它們分開來研究。在這個過程中我們學到的是：我們在多個資料集上做了測試，量測端到端延遲，同時也觀察了工具呼叫的次數與結果的品質。第一組是基準設定，也就是自動生成的一組工具。我們發現它的表現並不如預期，速度慢，而且結果品質相當有爭議。

後兩組我稱為「精簡版」（minimal）與「完整版」（full），它們是根據領域知識產生的，也就是依據我們對 Redis 查詢引擎運作方式的專業理解來設計。精簡版與完整版的差異在於，完整版是精簡版所有工具的超集合。舉個例子，如果你有一個像 GetShardInfo 這樣的工具，想找出哪個分片（shard）速度慢，你可能得先呼叫它，再對結果做一些後處理；相對地，完整版可能直接有 GetShardInfo 和 GetSlowShard 兩個工具，你只需要直接呼叫後者就好。有趣的是，完整版的表現並沒有比較好，事實上它反而更慢，品質也只是稍微差一點而已。

這某種程度說明了「工具過載」（tool overload）確實是真實存在的問題，更重要的是，我稱之為「工具正交性」（tool orthogonality）或「可分離性」的東西相當關鍵。也就是說，只要代理人在任何時刻無法判斷該呼叫 B 還是 C，就會出問題。所以，對於設定工具，我們發現其實它基本上就是精簡版，差別只在於我們把其中一部分工具挪到啟動階段就先呼叫。這樣一來，代理人在解決問題的過程中，只需要在較小的一組工具裡做選擇。

在這裡，設定工具版本與精簡版的表現相當接近，直到我們更仔細去檢視、深入研究它們各自的軌跡，才發現有趣之處：精簡版在沒有設定工具的情況下，軌跡其實不穩定得多，出現了更多獨特的序列組合。當然，並不是每一種獨特序列都代表問題，但其中有些確實會造成困擾。這裡的重點是：減少變體的數量、減少 LLM 在每個節點需要做的決策，能降低變異程度，也能提升一致性。而我們正是透過提供設定工具、強制建立新人訓練式的脈絡，才做到這一點。第二個面向，則是把知識組織成操作手冊。

那麼，這對我們的結果造成了什麼影響？我們大致把結果分成兩組——回答品質與軌跡品質。回答的根據性（grounding）與具體程度屬於最終結果的範疇，而首次嘗試成功率與死路比例則屬於軌跡本身的範疇。整體而言，當我們改用操作手冊、而不是直接讀取原始指南時，各項效能都有所提升。

我們也觀察到，權杖（token）總量減少了 43%，整體錯誤率降低了 48%。如果你看表格最後一列，有趣的是，它同時也讓代理人更能遵循指令。這裡要強調的重點是：讓代理人更容易存取資訊，不只降低了成本，也減少了「遺忘」的情況，進而提升了可靠性。當然，並不是所有事情都如預期般順利，還有許多可以改進的地方。其中一個很適合套用的方向，就是遞迴式自我改進（recursive self-improvement），這也是本次峰會上相當常見的主題。所以，我們大概還得朝這個方向繼續研究，進一步提升效能。

不過，我們確實看到許多常見失效模式的減少。最後，總結一下，如果要留給各位幾個重點，我想強調兩件事：第一，要衡量的是軌跡，而不只是最終答案，因為我們觀察到的許多問題，並不會顯現在最終結果裡，我們必須檢視軌跡本身。如果可行，把知識架構成方便代理人辨識與存取的形式，並檢視你的工具設計，區分哪些是必要的基礎脈絡（baseline context），哪些是自由裁量或探索性的脈絡。最後補充一點：如果你能同時做到結果的正確性、完整性與有用性，並且擁有高效率的軌跡，你的代理人就更有機會做到可上線、可靠的生產等級。
