這件事之所以困難，是因為許多舊版 Java 應用程式所使用的框架，會用它們的 API 把執行期行為（runtime behavior）隱藏起來。也就是說，這些框架會使用不同的代理（proxy）、反射（reflection）、攔截器（interceptor），而程式碼本身並不會真正記錄下這些機制，這些都是由框架自己處理的。因此，用 Spring 寫的應用程式和用 Jakarta 寫的應用程式之間，並不存在真正一對一的對應關係。當我們遷移這些應用程式時，看起來它們可以正確建置、正確執行，但其實可能存在一些靜默失敗（silent failure），要到部署時才會顯現出來。為了讓這個基準測試更有依據、說明它為什麼重要，我想先秀這張投影片，說明典型企業級 Java 應用程式的架構。

大型應用程式通常會按層（tier）組織，每一層負責特定的關注點。舉例來說，表現層（presentation layer）透過瀏覽器或手機應用程式把應用程式呈現給使用者，再往下則有資料存取層（data access layer）負責資料庫的讀寫，還有一個橫切關注點（cross-cutting concern），把設定、安全性等等全部串在一起。但這其實是一個相當棘手的問題，因為如果你觀察應用程式，會發現嵌入在裡面的行為與商業邏輯，通常都被藏在框架與其 API 背後，而每個框架都有自己的特殊之處。舉例來說，依賴注入（dependency injection）的註解（annotation）等等，決定了商業邏輯是如何嵌入的，如果我們試圖在程式碼裡尋找它，可能根本找不到。

雖然這些層在關注點上是分開的，但一個已部署的應用程式，這些層往往會同時互相互動，所以這是一個很有挑戰性的問題。為了解決這個問題，我們打造了 SCARF Bench，全名是 self-contained application refactoring benchmark（自足式應用程式重構基準測試），目標有兩個。第一，我們想了解代理人在把應用程式從一個框架遷移、現代化到另一個框架時到底有多有效；第二，在這個過程中，透過理解代理人的執行軌跡，我們想建立一份類似的實務手冊，說明如何為一般性的現代化打造代理型（agentic）解決方案。我們把這個基準測試分成兩組，我很快帶大家看一下。

我們有「聚焦型應用程式」（focused applications）和「完整應用程式」（whole applications）。聚焦型應用程式是針對我們剛剛討論的單一層所寫的獨立小應用；完整應用程式則是把這些層整合成一個完整的商業使用情境。這只是應用程式的高層概覽。我們在 IBM 做的事情是，找了很多領域專家（subject matter expert），手動把我列出的這些應用程式，跨 Spring、Quarkus、Jakarta 這些框架逐一轉換。這裡的每一列就是一個應用程式，遷移的單位可以是任何一個從某個框架換到另一個框架的應用。這麼做的目的有兩個：第一，每一種遷移都有自己的特殊之處，而且是不對稱的，Spring 遷移到 Quarkus 和 Jakarta 遷移到 Spring 是非常不一樣的。

我們也想了解代理人在處理各自獨立的層時效果如何。代理人可能非常擅長轉換表現層，但在整合層或資料依賴注入層可能就會卡住。就像我提到的，這些層各自是獨立的，但典型的已部署應用程式，是所有這些層的集合，而且這些應用程式往往彼此互相溝通、互相互動。所以我們基準測試裡「完整應用程式」的部分，捕捉了很多這類應用程式，同時涵蓋單體式（monolith）以及對應的微服務（microservice）部署，一樣是由領域專家手動跨這些框架轉換完成的。整體來看，我們大約有 38 個獨立應用程式，但這相當於同一個應用程式的 114 種變化版本，方向性的轉換加總起來大約有 228 種。

這點其實蠻直觀的，就是資料在技術上有多紮實，包括完整性、一致性和新鮮度。接著是語意與詮釋資料（metadata）：舉例來說，我們有沒有這個資料集的詮釋資料？假設我們在處理一個 Postgres 資料庫，我們有沒有資料表和欄位的註解，或是有沒有一個包含該情境脈絡的區塊？接下來是存取與治理（access and governance）：我們到底能不能存取相關資料，或者代理人能不能存取相關資料？結構整備度（structural readiness）：這就是我前面舉的那個資料主機資料庫的例子，我們發現那個資料集市（data mart）其實採用了實體屬性值（entity attribute value）這種概念，大家可以自己查一下這是什麼，但重點是，這種結構並不太適合在上面跑代理人。

接著我們還有可泛化性（generalizability），也就是探討這個資料層是不是可以泛化，能不能超越「快樂路徑」（happy path）去運作。基於這些，我們最近拿到了一個 NeurIPS workshop 的名額，我知道 Scale AI 也有另一個 workshop 獲得核准，恭喜他們。我們在巴黎拿到了一個 NeurIPS workshop 的名額，很期待能就這個主題多聊聊。基本上我們正在做的事情，是把整個社群凝聚起來，我們在為代理型 AI 打造資料基礎設施，同時也在為代理型 AI 打造評估與基準測試。大家可以上網看看，歡迎掃描 QR code。這其實是 Genentech 內部，以及外部學界、業界和社群共同合作的成果。

太好了。就像剛剛介紹的，我叫 Scott Clark，是 Distributional 的共同創辦人暨執行長，同時也在打造 Tolaria Scientific。我要跟大家聊聊，我們要怎麼獲得更好的富足，不過首先我要先定義一下這是什麼意思。透過 AI 帶來的富足，到底是什麼意思？在我看來，這代表更好的科學發現，帶來新材料、更有效率的能源，進而帶來更好的醫療、更有效率的交通方式，說穿了，就是活在一個科幻小說般的未來。這並不是要消滅更多白領工作、讓大家都失業，而是要如何改善大家的生活品質。而我相信，這是我們第一次真正有能力，用 AI 有意義地加速科學發現。

過去幾個月確實釋放出了不少能力。這是我長久以來的熱情所在，過去二十年的職涯裡，我一直試著解決這個問題，成效有好有壞。這要從我念大學部、一路到博士班說起，那段期間我解決的每一個問題、合作過的每一個團隊，從蛋白質摺疊、量子力學模擬到總體基因體組裝（metagenome assembly），最後都會碰到同一個問題：我們做出了很棒的東西，然後就得開始調參數，一大堆不同的旋鈕和拉桿，超參數（hyperparameter）之類的，隨便你怎麼稱呼它們。只要能讓圖表和基準測試的數字好看一點點，你就能發一篇更好的論文。

我們開玩笑把這個叫做「研究生梯度下降」（grad student descent），因為常常就是研究生熬夜坐在那裡，在一個高維空間裡調參數，只為了讓論文能再好看一點點。有人真的用了一些聰明的技巧，像是模擬退火（simulated annealing）、遺傳演算法、局部方法等等。我則愛上了貝氏最佳化（Bayesian optimization），它後來成了我博士論文的核心，也成了我第一間 AI 新創公司 SigOpt 的核心概念。這間公司創立於 2014 年，目標是解決參數調整的問題，在七年的時間裡，我們和許多優秀的公司合作，像是幫 Netflix 調整推薦系統、幫 Amex 調整詐欺偵測系統、在 OpenAI 還是非營利實驗室的早期，幫他們調整早期的強化學習系統，還有大約一兆美元規模的避險基金客戶，以及數百位學者用我們的免費方案來調整他們的論文。

從材料設計到藥物開發，什麼都有。2020 年我把公司賣給 Intel 之後，我們用它來調整從晶片設計到基準測試機器學習效能（bench-maxing ML perf）等各種東西，那時候大家都在瘋狂追求那個指標。所以目標是針對真正重要的問題，做到大規模的最佳化，而且成效確實不錯——除了失效的時候。問題在於，它會完全照你告訴它的去最佳化，永遠只針對你給它的指標去最佳化，但客戶常常回來跟我們說，對，你確實把那個數字拉高了，但另一個數字卻掉下去了。這就是最佳化器（optimizer）的問題所在：黑盒最佳化器最棒的地方，就是它會針對你給它的任何評估指標去最佳化。

而黑盒最佳化器最糟糕的地方，也是它會盲目地針對你給它的任何評估指標去最佳化。所以你其實可以做出一個看起來準確度很高的詐欺偵測系統，只要你的交易裡只有 1% 是詐欺，你只要說「全部都不是詐欺」，馬上就有 99% 的準確率。此外，我們距離讓這些系統完全自主運作，還有很長一段路要走。我認為我們離「給它一個目標，讓它自己去解決穩定局限的圍堵問題、解決癌症」這種事情，還有很長的距離。而且就算模型真的給出了一個答案，我們要怎麼相信它？這就是這個問題的另一面：你既需要最佳化這些系統，也需要能夠信任它們。而這正是我創立 Distributional 想做的事。

我一開始想用最複雜的數學方法來解決這個問題，用大型統計檢定，想要解決混沌（chaos）和非穩態（non-stationarity）的問題，結果這是個很糟糕的主意，因為沒有人喜歡做檢定，他們也沒有足夠的資料，而且大家反正都是直接把模型 YOLO 上線到正式環境。所以我把公司轉向了，這就是創業，失敗了就轉型（pivot），轉去做分析（analytics）。所以我們想，來抓住那些偷偷溜過你系統的評估漏洞吧，看看能不能從行為模式裡找出規律，告訴你「嘿，這是一個你根本沒想到、但應該要寫的評估」。結果這個也失敗了，這其實是個很好的點子，但它頂多算是一個功能，稱不上是一個產品，更稱不上是一間新創公司。所以我現在做的事情，是把過去二十年學到的一切，拿來攻克「我們該如何加速科學發現」這個問題，聚焦在真正重要的事情上，打造懂物理學、懂科學研究流程、懂如何做假設驗證的量身訂做評估，這樣你就能讓「假設驗證機器」的飛輪越轉越快，把我在研究所時期要花六個月才能做完的事情，變成六個小時就能完成。

如果你對這個有興趣，我們正在公開地打造這個系統，它會在 NeurIPS 上開源，現在已經有私人測試版了，歡迎持續關注，如果你在做任何跟計算科學相關的東西，我很樂意跟你聊聊。好，謝謝大家留到現在。今天最後一場演講，由 Uber 產品負責人 Aayush Agrawal 帶來「評估：代理人改進的引擎」。太棒了，先跟大家鼓個掌，因為你們留到了最後，這是一整天的活動，我真的很佩服大家能留到現在，所以先謝謝大家留在這裡。我很清楚，我現在就是擋在大家和外面美好的柏克萊天氣之間的那個人，所以讓我們先來暖暖場，看看現場都有哪些人。

首先，來個超簡單的問題：今天有誰搭過 Uber？請舉手示意一下。好，有一些人，太好了。更重要的是，有誰真的在正式環境裡為代理人寫過評估（eval）？來看看現場有哪些是真正的建造者。好，不錯。最後一題，這題你們可以為自己感到驕傲：這些評估有沒有告訴你一些東西，進而改變了你們產品出貨（ship）的方式？好，太好了，太好了。所以，把評估當成一個打勾的檢查項目，跟評估真的能改變你的產品方向，這兩者之間的差別，正是我們在 Uber 花了一年多的時間，努力想確保每個代理人團隊都能做到的事情。今天我就是要跟大家聊聊這個。在 Uber，我們一直在整個生態系裡不斷推出代理人，包括對外的代理人，像是你可以用語音叫車，也包括對內使用的代理人。

而在企業規模上驅動這一切的，是我管理的 Uber 代理人平台（Uber agent platform），裡面有很多不同的元件，讓代理人團隊不用去煩惱基礎設施的問題。而我今天要講的，就是評估（eval），這正是這整個議程廳都在關注的主題，真的很令人興奮。我們觀察到一個普遍現象：每個團隊都想要高品質的正式環境代理人，但他們一開始都會做同一件事——他們會說，「欸，我先把代理人上線，評估的事之後再說」。這其實是一個很理性的決定，因為對他們來說，他們就是想先證明產品市場契合度（product market fit），先看看這東西到底能不能用。

但這麼做的結果，就是他們陷入一個無止盡的循環：事後才回頭補評估，然後拚命想搞清楚為什麼代理人壞掉了。所以我們發現，團隊真正遇到的摩擦點，正是阻礙他們更早進入良好狀態的原因。而我們身為平台團隊，就決定要為他們把這些摩擦點消除掉。那我們就來聊聊，怎麼讓評估變成預設值。第一件事，這在今天的議程裡也一再被提到，就是從追蹤（tracing）開始。我們的做法是，確保從第一次開發開始，每一個環境都有追蹤機制。這讓團隊能夠理解、並且有一個基礎，來建立之後其他的評估。

他們可以直接打造一個代理人，靠感覺（vibe）調整它、把它送出去，而它隨著時間演變的所有資訊都在那裡，不需要事後再去補。第二點是，一旦他們能拿到洞察、拿到資料，接下來就是要知道怎麼從中得到洞察。團隊常常不知道該怎麼開始寫評估，不知道最好的寫法是什麼、也不知道該從哪裡下手。所以我們的做法是，利用我們掌握的代理人建置脈絡、相關文件，找出最適合的入門評估器（starter kit evaluator），然後直接把這些洞察送到建置者的 Slack 頻道，讓他們能夠理解，「嘿，我雖然不知道什麼是 LLM 評審（LLM judge），但我知道工具矛盾（tool contradiction）是什麼意思，也知道該因此做出什麼改變」。
