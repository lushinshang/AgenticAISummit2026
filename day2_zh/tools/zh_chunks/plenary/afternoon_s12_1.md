這八家公司今天都會來到現場進行簡報。除了這八家公司之外，我們也很榮幸邀請到另外四家來自業界的早期 Agentic AI 公司一起參與。那麼，話不多說，讓我快速介紹第一位上台的公司：Narada AI。Narada AI 正在為企業打造 Agentic 自動化技術，讓 AI 代理能夠端到端地執行跨 SaaS 與舊有系統的複雜工作流程。話不多說，讓我們歡迎 Narada AI。大家好，我是 Dave Park，Narada AI 的執行長暨共同創辦人。我想跟大家聊聊，我們如何協助越來越多的客戶——包括製藥與科技業的財星百大企業、橫跨汽車、飯店與醫療產業的財星五百大企業——部署能夠可靠、穩健且具成本效益地執行他們最複雜工作流程的 AI 自動化系統。

我們剛創立公司的時候，做了成百上千場客戶訪談，想了解為什麼人資、IT 與財務部門有這麼多流程至今仍高度仰賴人工。這些並不是那種簡單的 co-pilot 型任務，大部分的痛點其實在於長流程的作業，例如 ERP 測試、跨多個資料孤島的資料驗證與核對，以及橫跨多個生態系、舊有應用程式、SaaS 入口網站、甚至網頁的訂單、發票與帳單核對與處理。而且因為許多步驟的 API 十分有限，這代表必須透過使用者介面操作，用視覺方式判讀畫面上的內容，進行點擊、輸入與捲動。而傳統的自動化做法，像是寫死的腳本與機器人流程，只要介面一有變動就會頻頻故障。

另一方面，通用型 AI 模型在處理過程中，常常因為混亂的正式環境裡各種可能出現的現實例外與問題，而在流程進行到一半時開始產生幻覺。像是登入問題、連線中斷、逾時、應用程式設定變更，甚至是 CRM 這類記錄系統裡多筆重複資料的去重處理，都可能讓模型出錯。

為了解決這個問題，我必須找來這個領域裡一些最頂尖、最聰明的人才一起合作。我第一次創業是在史丹佛主修資工博士的時候，公司叫 Quiverity，成果還算不錯。但這一次，既然我更成熟、也更有經驗了，想打造一個規模大上百倍的事業，我需要找柏克萊最優秀、最聰明的人才一起合作。於是我找上了 Kurt Koitzer，他是柏克萊資深的 AI 教授，還有 Amir Ghulami，他在柏克萊 AI 實驗室主導了 Narada 背後的研究工作。在頂尖投資人的支持下，包括 Monta Vista Capital 的 Veng Shukla，以及多家全球頂尖 AI 公司的共同創辦人與執行長，我們正在打造 Narada。

Narada 是一個專為企業應用與工作流程打造的 Agentic 自動化平台。我們運用專有技術，自動繪製出客戶應用程式與介面的設定地圖。只要根據這些流程的自然語言描述，甚至只是螢幕錄影，Narada 就能動態產生為客戶環境量身打造的代理。第二，為了達到高準確度與高穩健性，我們把過去所學到 AI 代理為何會失敗、又會在哪裡失敗的經驗，全部拿來打造測試環境與訓練場域，運用合成資料開發並測試各種執行環境，讓系統能從流程中任何一個環節可能出現的現實世界例外與問題中恢復。

我們運用一項新的研究成果，這是一個叫做 LLM compiler 的 Agentic 規劃與執行框架，讓我們能夠把這些長流程任務拆解成許多細部步驟，並在每一步都納入單元測試、例外處理、防護機制與自我修復，確保這些自動化流程始終不偏離軌道。最後，這一點很重要：我們用來繪製並學習客戶特定設定的相同機制，也可以用來最佳化大量的工作負載。所以，在我們真正繪製出跨不同介面的執行路徑之後，接下來處理成千上萬筆訂單、理賠的後續迭代時，就能用少得多的運算資源，以更高的速度與準確度，為客戶帶來規模化與成本效益。

因為並非所有系統都有 API，我們擁有非常精準的電腦操作代理，幾乎可以透過任何介面運作。它可以操作舊型的綠幕應用程式，也可以透過瀏覽器型的應用入口網站與 SaaS 工具運作，甚至可以透過 Citrix 操作遠端桌面。而這一切不只靠電腦視覺完成，只要有可能，它還會分析底層的 HTML 與 DOM，理解該頁面完整的內容脈絡，甚至能看到隱藏的元素，藉此進行點擊、輸入、捲動來執行這些流程。讓我示範一個例子。這裡因為 API 有限，Narada 實際上能透過自然語言指令，非常有效率地操作像 ERP 系統這類內部應用程式，過程中持續進行單元測試、驗證例外處理，並針對可能發生的設定變動進行自我修復。

這是我們某個客戶的使用案例，他們需要橫跨 23 個不同國家，列出競爭對手不同車款的規格，擷取所有配備與價格資訊，藉此了解競爭對手的定價方式。這類任務需要數百個步驟，而且準確度要求非常高。最後，來看看我們能帶來的規模化與成本效益：Narada 可以進入像這樣的新介面。這是我們某個客戶的案例，他們有 4,000 個這類型的帳單入口網站，因為沒有 API 支援，必須透過使用者介面操作。Narada 會先繪製並學習如何透過這個介面執行這個流程。一旦學會如何透過這個介面處理帳單，之後所有後續的迭代與變化，都能用少得多的運算資源，以更高的速度與準確度處理，為客戶帶來成本效益。

所以如果你有訂單處理、測試與驗證、發票核對等使用案例，歡迎來找我們聊聊。我們可以在幾天之內免費交付概念驗證（POC）。就算你不是企業的一員，而是自己在打造 Agentic 系統與框架，如果你想運用我們精心打造的測試環境與合成資料來訓練並最佳化你的代理，我們也很樂意跟你聊聊。歡迎寄信到 Dave at narada dot ai，或是寫信到 info at narada dot ai 跟我們聯絡。非常謝謝大家。

接下來是 cognee。cognee 是一個開源的 AI 記憶層，透過向量與知識圖譜，賦予代理持久的關聯與推理能力。讓我們歡迎 cognee。

嗨，大家好。

我是 Vass，cognee 的創辦人。我從柏林飛過來，想跟大家聊聊我們在打造什麼，以及我們如何處理 AI 記憶這個議題。AI 記憶最近是個很熱門的話題，我今天在各場座談上聽到很多次，用不同的方式被提起。我想解釋一下我們是怎麼看待這個詞的，以及我們對它的整體理解。過去 90 天內，我們在 GitHub 上獲得了將近 8,000 顆星，我們開源的 Python SDK 已經產生了 800 萬筆記憶。我們有來自布朗大學與柏克萊的研究員與博士後研究員，協助我們用類似人類的方式調節記憶。我們這麼做，是為了解決一個特定的問題：在不耗盡 token 的情況下，我們能不能在任何 harness、任何模型裡加入一個自我改進的迴圈？

而這個問題，從我們的角度來看，其實不是一個 Agentic 問題，而是一個資料問題。代理產生的資料量是人類的 100 倍。Agentic 工作流程的資料密度非常高，需要產生大量的上下文。但我們同時也有傳統的資料系統，像是 CRM、資料孤島，這些也需要被連接起來，讓代理能夠據以推理。這一切都讓我們需要新一代的資料系統，能夠有效連接並處理代理產生的資料，同時把它跟組織裡既有的資料、以及使用者資料整合在一起。舉例來說，如果我們以 Sam 為例，他想送花給「他」，問題永遠都在於，一旦我們用代名詞「他」，我們其實不知道指的是誰。

「他」在不同的日子裡可能指涉不同的人。在這個情境裡，也許是 Codex 要送花給 Dario，而我們都知道，或者說我們都清楚，他們彼此的關係並不是很好。這種對於特定實體的定義問題，像是營收、財年、會計年度、業務領域用語，還有你個人的偏好與習慣，正是 cognee 要解決的問題。而我們解決這個問題的方式，聚焦在以下幾個面向：情感狀態、版本、時間性、不同代理以不同記憶進行的並行讀寫、衝突解決、時間感知與時間戳記，以及在某個時間點所代表意義的後設表徵，還有人們應該如何與這些事物互動。

我們的做法，基本上是建立一套資料管線，將資料擷取、結構化並處理成一組圖形向量表徵，你可以把它想像成千層麵（lasagna）：把一層層的語意疊加在一起，彼此交叉連結，並持續演進，藉此從傳統資料倉儲那種固定的事實維度綱要（fact dimension schema），轉變成一個不斷向前推進、持續演化更新的綱要。在代理出現之前的上一代做法，這叫做特徵儲存（feature store），但傳統的特徵儲存相對靜態。我們所做的，是打造一個能自我改進、自我演化的特徵儲存，讓你能夠有效地持續更新，並在不同的 harness、不同產業的各種任務中運用大型語言模型。

所以 cognee 就坐落在你的資料與 Agentic 工作流程之間，我們把自我改進的能力內建在裡面。這代表我們可以隨時更新這些綱要，隨時加入更多層次與更多上下文，了解代理在哪裡失敗、了解公司資料或你的個人資料在哪裡沒有更新、或是在哪裡發現了衝突，而這一切都建立在 Postgres 之上。所以如果你只想在 Postgres 裡跑，不想搞一堆資料庫，也完全可以；但在我們這邊，每個代理都可以有自己的資料庫，每個團隊、每個租戶、每一群你想定義的使用者都可以各自獨立，而這一切在開源版本裡都支援。舉例來說，這裡我們有一個 cognee 搭配 Claude Code 的外掛，你可以看到，如果你直接用 Claude 進行推理，會需要花上一些時間。

但用了我們的方案之後，取得上下文的速度快上許多，準確度也高上許多。我們在 Beam 這個業界標準記憶基準上做了測試，目前在業界拿到了頂尖的分數。同時我們也能節省 token：相較於把整段上下文硬塞進去，我們能幫你省下 86% 的 token。從年初到現在，我們的 GitHub 星數從大約 1 萬顆成長到 3 萬顆。SDK 每個月額外有 800 萬次執行，上個月下載次數大約 17 萬次。而我們本質上是一個開源工具，可以搭配任何一種 harness，提供 API 與 CLI。你可以自己試試看，我們有 Rust、TypeScript、Java 版本，你可以自行架設。如果你的組織需要更完整的功能，也可以把 cognee 架設成伺服器，開始在代理之間、使用者之間、團隊之間共享資料。

這正是我們相當擅長的部分。歡迎隨時聯絡我，加入我們的 Discord，或加入我們線上的社群，參與我們的活動。我們會辦黑客松，努力推動這個領域的邊界。我的時間差不多到了，祝大家今天愉快，謝謝各位撥冗聆聽。

接下來是 Nimblemind，他們正在打造醫療領域的 AI 代理。讓我們歡迎 Nimblemind。

大家好，今天過得怎麼樣？我叫 Paisa News，是 Nimblemind 的共同創辦人暨執行長。謝謝 Dawn、Linda、Will 還有 RDI 團隊的邀請，很榮幸今天能來到這裡。喔，這是我的最後一張投影片。可以幫我……好，我找到了，我們倒回去。好，沒問題。那我想先暫時跳出科技的世界，聊聊在座每個人都會接觸到的東西：醫療照護。全世界，不只是這個國家，都面臨一個巨大的醫療問題。這是一個嚴重的產能問題：沒有足夠的臨床醫師與受過訓練的人力，能夠為地球上所有人看診與治療。光是在美國，我們花在行政作業上的支出——也就是那些跟臨床醫師或病患實際照護無關的事務——就占了大約 25%，相當於美國國內大約 6,000 億到 1 兆美元。

這是個非常龐大的問題，而我們認為 AI，尤其是代理，是我們目前所擁有、最適合解決這個醫療成本嚴重膨脹問題的方案。醫療照護這幾十年來已經改變了很多。如果回想大約 50、60 年前的醫療型態，那是醫師與病患之間單純的一對一關係。但醫療照護已經演變了，照護路徑改變了，由於每個人獨特的生活型態與基因，治療每一位病患都涉及大量的資訊與複雜度。而你還必須把這一切，跟後端的計費系統結合起來：你必須做好適當的編碼，還要向保險支付方取得正確的授權。

要提供照護，個人或系統必須完成成千上萬項任務，而這些任務未必是病患與臨床醫師之間那種診斷關係本身。這正是 Nimblemind 首先要解決的問題：我們該如何最佳化這些流程，打造出高品質的工作流程，把這些任務自動化，讓臨床醫師有更多時間陪伴病患？要做到這一點並不簡單。很多人已經導入了 co-pilot、把大型語言模型帶進這類工作流程，但都缺少三個關鍵要素。你必須能夠執行可預測、結構化、一致的任務；你必須以系統化的方式讓人類參與決策迴圈，在適當時機把低信心度的判斷交給專家處理。

接著你還需要打造以目標為導向的工作流程，而醫療領域裡有非常多這樣的情境，非常複雜。這正是 Nimblemind 的獨門秘方：我們把這三個要素整合在一起，把我們稱之為端到端醫療知識工作的部分自動化。我們會在提供者所擁有的各種龐雜系統中，找出相關資訊；理解脈絡與例外情況；完成多步驟的工作流程，並標示出可能需要人類介入的地方；最後回傳一個可追溯的結果給使用者。而我們做到這一點的方式，是靠專科別的專屬模型。我在上台前在後台休息室跟 Matt White 聊過，他大概三、四個場次前才在台上分享過，來自 Linux Foundation。

他跟我都認同，這種小規模、特定領域的專屬模型才是未來的方向，這也是我們在做的事。我們正在訓練並打造符合現今醫療實務——也就是各個專科——的專屬模型。我們有針對腫瘤科、病理科、放射科、腎臟科的模型，還有一長串沒有列在投影片上的其他科別。透過把這些模型結合在一起，打造出一個由多位「專家」組成的系統，我們能夠在醫療領域完成高品質、一致且可靠的任務，贏得臨床醫師的信任，為病患帶來正確的結果。那有沒有具體的例子呢？我們最近跟新加坡保健集團（SingHealth）一起發表了一篇論文，我會在 10 月 8 日於這裡的舊金山 DAIH 研討會上發表這項成果。
