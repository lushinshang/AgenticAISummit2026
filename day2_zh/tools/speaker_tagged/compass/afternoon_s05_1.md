**主持人：** 接下來由 Postman 現場技術長 Rick Crawford，為大家帶來「從代理人展示到生產環境：Postman 如何構建可靠的 AI 代理人基礎設施」。

**Rick Crawford：** 再次感謝各位撥冗，來了解我們如何從原型走到生產環境，並交付一個真正在 Postman 內部創造價值的代理人。這是一條在座各位如果正在打造代理人，可能都很熟悉的曲線。我們原本是一個在開發流程上非常「代理人優先」的組織，但我們意識到，我們想要開始打造能在組織內做出決策或提供協助的執行時期（runtime）代理人。所以，我們開始做原型，並找出業務中可能可以產生影響的不同領域。

**Rick Crawford：** 從那之後，我們開始獲得一些初步的關注，不論是來自執行長還是董事會，他們找上我們說，嘿，我們真的想要推進，並把其中一些落實到組織裡。但接下來更大的挑戰來了：好，那我要怎麼衡量這個？我要怎麼管理這個？我要怎麼確保我們交付的東西是可以維護的？所以，這時候像是判斷投資報酬率（ROI）與營運成本之類的議題就開始出現了。所以，我們這次想要解決的問題領域是企業銷售。這個領域的好處是，它有一個非常明確定義的流程，從發掘商機到續約，中間都有明確的步驟。

**Rick Crawford：** 透過這個流程，有大量團隊一起合作。我們遇到的挑戰是，這些團隊之間很難把資訊脈絡（context）交接給彼此。當你去看這些成員與團隊實際使用、串接的系統數量時，那根本就是一大群系統，對吧？困難的地方在於，要搞清楚這些系統之間資料的關聯是什麼。最終，我們得到的是一個不透明的流程，每一步都會流失一些脈絡。所以，從我們組織的角度來看，我們想搞清楚：嘿，我們能不能打造一個可以在整個銷售流程各階段都幫上忙的代理人？

**Rick Crawford：** 所以，我們做了每個工程組織都會做的事：辦了一場黑客松（hackathon）。我們把這件事開放給工程師們，短短 30 小時內，他們就打造出了一堆代理人。但這裡看到的，就是一大群不同的系統、連接和代理人。最終，我們找出了一個「勝負分析代理人」（win-loss agent），它確實能給我們一些相當有趣的結果。從這裡，我們歸納出三個核心問題。第一個核心問題是，我們發現結果越是……不對，我是說，結果越是確定性（deterministic），代理人的表現就越好。以勝負分析代理人為例，我可以得到像是「這是我們輸掉這筆客戶的原因」這樣的結果。

**Rick Crawford：** 我可以從代理人給出的結果往回推理，然後說，對，這聽起來差不多對。也許是我們的價格太高了，所以才輸掉那筆交易。但如果我拿同一個代理人去問：好，那產生潛在客戶（leads）最好的方法是什麼？它就開始有點失控了。它會開始產生一些我們很難判斷對不對的結果。我們發現的另一件事是，模型越複雜，回傳的推理就越好，但同時要理解那些結果也變得更加困難、更容易混淆。第二點是，這其實是一個會不斷疊加放大的問題。

**Rick Crawford：** 在座如果有打造過微服務架構的人，可能會對這個很有感。A2A（代理人對代理人）與代理人、社群代理人——我們發現，我們最終同時面臨疊加的成本與疊加的混亂。而這些代理人之間交接與測試的挑戰，也變成一個更大的問題。最後，我們發現的另一件事是，這其實是一個分解（decomposition）的問題。我們原本的做法是分別打造一個個獨立的代理人，卻沒有意識到這些代理人其實都屬於同一個領域。如果在座有 Martin Fowler 的粉絲，熟悉設計模式的話，應該會認出這就是分解模式。我們發現，這些系統之間的介面，以及脈絡的交接，才是最大的挑戰。

**Rick Crawford：** 所以，我們有了這三個問題，而我們的做法是，提出一個包含四個解決方案的框架來因應。在最底層，我們打造了一個單體式（monolith）代理人。這個代理人掌握了與銷售流程相關的所有知識與資訊。Salesforce、通話記錄，它可以拉進逐字稿，我可以問它一些很有趣的問題，並得到有趣的結果。所以，這確實是個很棒的副駕駛（copilot），是個很棒的答案產生器。但我們遇到的挑戰是，如果有些灰色地帶，它就會開始亂編。它是個很友善的東西，但如果我開始問它更專業的問題，它掌握的資訊就太多了，反而給不出正確的結果。

**Rick Crawford：** 所以我們在此基礎上繼續打造。下一階段是分解元件。我們在這裡實作了兩個關鍵部分。第一個是幻覺層：除非你清楚知道資訊來源是哪裡，否則不要提出建議。如果你不知道，就必須清楚說明你是怎麼得出這個結果的。如果兩者都做不到，我們就直接忽略它。除此之外，我們還想打造那些特定領域的代理人。這不是一個寫程式的任務，而是一些提示詞（prompt），我可以進去說：嘿，我是個業務人員，這些是我平常會做的事。然後它就會針對那個角色去回答相關問題。

**Rick Crawford：** 這讓輸出變得更精準，也不再產生那麼多幻覺，但它卻是「自信滿滿地錯」。知識與智能，不等於策略。所以，如果我問業務代理人：我應該賣給哪種角色（persona）？在座各位有人猜猜看嗎？通常負責採購軟體的角色是誰？沒錯，就是這樣。所以它會回答：每次都賣給採購部門。但如果我真的走進客戶那裡說，嘿，我要賣給你們的採購部門，他們會把我們笑出會議室。所以，這時候我們開始找出真正擁有那些策略性內容的團隊，並讓他們負責補充那些資訊。在這個案例中，業務團隊會進去補充他們的客戶規劃（account plans）。

**Rick Crawford：** 而現場工程組織則會補充諸如他們的解決方案如何運作之類的內容。從這裡開始，這些代理人得到的資訊變得越來越具策略相關性，輸出也變得越來越重要。但挑戰在於，這時候我有了一個理解整個組織的超級代理人，卻沒有任何管控機制。這就是我們實作最後一層的地方：超越「這個對不對」或「這是不是真的」這個模型層次。我們需要再加一層，問：這個內容，跟提出請求的這份工作有關嗎？這樣一來，如果我去問技術長（CTO）代理人，它就不會把公司損益（P&L）相關的所有資訊都告訴我。

**Rick Crawford：** 它會考量我的脈絡與職務角色，只給我跟我相關的資訊。而這麼做帶來的結果是，讓我們找出了幾個真正想要投入、開發更多代理人的方向。我們也真正定義出所謂的「代理人自主性曲線」（agent autonomy curve）。在每一個階段，它都要判斷：是人類還是代理人在做決策？這裡有兩個決策要發生：誰來提出資訊請求？誰來決定何時把它升級（promote）？在「協助（help）」這個層次，人類同時參與這兩者：我提出問題，我分析結果。在「建議（recommendations）」這個層次，代理人開始接手這件事。但發生最大躍進的地方，是介於「執行（act）」與「擁有（own）」之間：在「執行」這個層次，代理人在某些防護機制內，同時處理這個等式的兩端。

**Rick Crawford：** 而最終，「擁有」這個層次，才是我們所有人都在努力朝向的目標，也就是擁有能夠長時間運作、並全權負責整個生態系的長效代理人（long-running agents）。而我們從中看到的結果，其實相當令人驚訝：我們的組織開始出現疊加的價值。我們從一開始花 30 小時黑客松打造出一個代理人，發展到現在有了這套框架，只要短短幾個小時，任何人都可以進去建立防護機制，並在我們已有的知識基礎上繼續打造。而在使用端，我們從原本只有一小群使用者能運用這些代理人，發展到現在整個組織都能找出自己該如何從中獲得價值。

**Rick Crawford：** 所以，我們在打造這些代理人所需的時間上得到了疊加的價值，在能從中受益的人數上，也得到了疊加的價值。而這麼做的另一個核心好處是，我們也看到組織裡行為上的改變。因為業務人員現在知道，他們建立的脈絡與提出的問題，也有助於這些代理人的底層價值，所以我們看到更多的探索行為發生，也看到內容的品質變得更好。如果我沒提到我們也打造了一個平台來協助解決這個問題，那就有失公允了。我們把這些學到的經驗，用來打造一個平台，讓我們能夠在組織內部打造這些持續疊加價值的代理人。我們也發現，最終，我需要能夠衡量正在發生的成果，需要有一份可用代理人的目錄，讓我的團隊可以「雇用」、「解雇」，並理解其影響——不論是在成本面還是投資報酬面。

**Rick Crawford：** 說到這裡，感謝各位今天撥冗聆聽。非常謝謝大家。如果有任何問題，歡迎在 LinkedIn 上跟我聯繫。非常感謝。

**主持人：** 接下來，是 Amazon 應用科學（邊緣 AI）總監 Rahul Bakshi，為大家帶來「根據訊號擴展運算」。

**Rahul Bakshi：** 你們聽得到我說話嗎？現在呢？我們再試一次。現在聽得到嗎？可以？好，大家早安。我叫 Rahul，我在 Amazon 帶領應用科學團隊，負責打造我們的客製化晶片。我們最新一代的晶片 AZ3，為我們去年秋天推出的 Echo 裝置提供動力。所以，可以想見，我大部分時間都花在思考邊緣運算、邊緣裝置，以及整體的邊緣規模處理。

**Rahul Bakshi：** 這也會是我今天演講的主題。過去幾年，我們一直在討論：如何為代理人取得更多運算資源？這是個重要的問題，因為它能解鎖新的能力。但今天我想把這個問題反過來問：如果因為物理限制，根本沒有更多運算資源可以給我們的代理人呢？這會是我今天演講的主題之一。另一個主題是，其實很多這類邊緣代理人，並不需要前沿等級（frontier-level）的智能或運算能力。而我們能在非常、非常有限的功耗預算下，做一些有趣的最佳化，來打造應用場景。好，讓我們來談談運算的擴展。我們要怎麼給代理人更多運算資源？

**Rahul Bakshi：** 其中一種方法是建置更多資料中心。過去幾年，我們都看過相關的新聞循環。Amazon、其他超大規模業者（hyperscalers）、新興雲端業者（neoclouds），大家都在打造越來越多的超大型工廠（gigafactories），來給代理人提供更多運算資源。這是其中一個槓桿。但在另一端，其實存在一個真實的功耗天花板。我會用可穿戴技術作為這個天花板最極端的例子，因為那裡的限制最嚴苛。想想任何一種穿戴式裝置，像是智慧手錶、智慧眼鏡、智慧戒指等等，它們通常只有大約 1 到 1.5 瓦的功耗可以運用。原因是生理限制：人類皮膚無法忍受超過攝氏 43 度的高溫而不開始灼傷，而且會變得非常不舒服。

**Rahul Bakshi：** 所以，那就是我們在邊緣端必須面對的硬性天花板。而邊緣與雲端之間的不對稱，我認為正是下一代混合架構創新的沃土。那我們來看第二個觀察。如果各位認同這個天花板，如果這就是我們必須面對的邊界，那麼在邊緣規模裝置上執行的內容，大致可以分成三個功耗層級。在最底層、也是最節能的層級，是在訊號源頭就進行處理。想想微小的喚醒詞偵測器，想想事件相機（event cameras），你在來源端就偵測，耗能極低。到下一個層級，你想拿這個訊號做什麼？

**Rahul Bakshi：** 如果你需要跑一些演算法，或需要跑一些工具呼叫（tool calling）工作流程，那就需要下一個等級的能量。仍然是在邊緣裝置上運行，但注意，這時消耗的功耗會高出好幾個數量級。最後，如果任務需要裝置上沒有的脈絡，或需要世界知識，那你就要動用資料中心等級的運算資源，那又會再高出好幾個數量級。所以重點是什麼？重點是：只有在任務真的需要時，才升級（escalate）。接下來我要分享的觀察，會得到同樣的結論，但用幾個不同的角度來看。今年稍早，柏克萊有一個函式呼叫排行榜（function calling leaderboard），追蹤不同模型的函式呼叫效率。

**Rahul Bakshi：** 我們看到的是，一個小型語言模型，在函式呼叫任務上，竟然能達到前沿等級的運算表現，也就是前沿等級的效能。這個任務追蹤的是函式呼叫的基本要素：產生的 JSON 是否有正確的函式、正確的 API、正確的參數。但重點是，對於定義明確的小型任務集合，我們確實有一條路徑，能在邊緣規模裝置上取得前沿等級的智能。再看看圖表的右側。過去十年間，透過無線網路傳輸一位元資料的成本，已經下降了非常多倍。然而，沒有以類似倍數下降的，是無線電（radio）本身的成本。所以，這兩個數字，都再次說明了功能分配應該落在哪裡。

**Rahul Bakshi：** 升級到下一個層級，不論從能耗還是電池續航力的角度來看都很昂貴，所以應該只有在必要時才這麼做。那麼，機會在哪裡？我認為這個迴圈其實已經建立超過十年了。如果你看 Amazon、Apple、Meta 的語音助理，大多數都有一個分層遞升（cascaded）的架構：先偵測喚醒詞，只有在必要時才逐步升級。目前缺少的，是一個可組合的執行時期（composable runtime），這也是我對在座各位的一個行動呼籲。舉個例子：你問你的助理，嘿，我的班機是幾點？會誤點嗎？這時候，如果執行時期夠聰明，知道要完成這個任務，我不需要開啟任何感知感測器、攝影機、麥克風，我只需要開啟無線電並做一次 API 呼叫，那就可以建立一個功耗預算，函式呼叫也能採用某種動態排程。

**John Liu：** 那典型的模型最佳化循環長什麼樣子？首先，你會先在客製化硬體上打造出一個可運作的模型。接著，你會調整一些模型層級與硬體層級的設定選項，例如改變平行化方式、改變序列長度、批次大小（batch size）。然後你會做效能分析（profile），對吧？分析並觀察效能表現，根據結果進入一個循環，繼續調整更多東西。到了某個程度，你會把這些開箱即用的選項調整到極限。這時候，你就會進入核（kernel）開發層級——把 kernel 想成是能讓你在硬體上解鎖更多效能的客製化函式。同樣地，你會調校它們、分析它們，形成第二個循環。但這樣還沒結束。

**John Liu：** 一旦 kernel 最佳化完成，你其實還需要做端到端的模型評估，確保它真的能運作。這樣你就完成了另一個循環。所以你可以看到，這其實是一個多層、多變數的最佳化問題，非常適合用循環方式處理。我們也發布了一些開源的代理人與技能（skills），協助客戶把原本要花好幾週的工作，縮短到幾乎只要幾個小時。這些技能能幫助大家在 AWS Trainium 上打造可運作的模型、撰寫 kernel、分析 kernel，而現在我們也在著手處理最佳化循環的部分。那我們就來深入看看其中一個最佳化循環——kernel 最佳化循環。這是一個常見的架構，對吧？我們使用所謂的「規劃者（planner）與執行者（executor）」模型。

**John Liu：** 我們循環想要逼近的目標，是硬體在你特定模型上能達到的最大效能，與目前之間的差距。從第零步開始，還有另一個循環，會針對特定的推論工作負載，找出最佳設定，並把它傳給我們的規劃者代理人，這是第一步。規劃者代理人會檢視這個設定，衡量與效能上限（roof line）之間的差距，並查閱它的本地知識庫，找出最佳的最佳化方案（optimization campaigns）。它把這些方案傳給執行者代理人，由執行者代理人負責執行這些方案。接著，根據執行結果，把結果記錄進知識庫：這個 kernel 有沒有成功？有沒有失敗？限制條件是什麼？然後我們再衡量整個端到端模型的效能。

**John Liu：** 最後，根據這些結果，我們決定要「晉升」還是「淘汰」這個 kernel，當然也會更新知識庫。這樣就完成了一個循環。接下來，我想分享一些我們在打造這些循環過程中得到的心得，希望這些心得不只適用於這種專業領域，也能套用在大家自己的循環上。第一點，一個你們應該已經聽過很多次的反覆主題是：代理人在「作弊」這件事上，非常有一套，對吧？只是告訴代理人「不要作弊」是不夠的。建立保留資料集（held-out data sets）、確保代理人沒有在死記硬背，這些只是基本做法。你真正需要思考的是，你代理型工作負載的每一個環節，都有可能被那個代理人操縱，尤其是你用來衡量效能的那個環節。

**John Liu：** 第二個心得是，每當你的代理人失敗時，不要急著直接去修那個代理人本身，先檢查它的可見範圍（visibility scope），對吧？在我們的一個案例中，那個代理人其實把 kernel 的本地記憶體用量最大化了，這本身是正確的決策，但它卻影響到了模型上其他正在運行的 kernel 所共用的記憶體。所以，在設計代理人的行動時，一定要檢查它的可見範圍。第三，當你在建立這些知識庫時，每當出了問題，要先檢查是不是你既有的某條規則造成了這個錯誤，去修改或刪除那條規則，而不是只是再加一條新規則，因為這樣只會讓代理人被越來越多規則搞得更混亂。

**John Liu：** 還有一個相關的主題：你手上的知識庫是有保存期限的。在專業領域中，這個知識庫在一開始能幫代理人快速上手，非常有用。但隨著模型的一般訓練逐漸跟上，就會開始出現某種衝突，你的代理人會感到困惑：我該用知識庫，還是該用模型本身的訓練內容？所以，一個好的做法是持續移除知識庫的內容，並檢查代理人的表現。如果表現反而提升了，那就是該修剪那個知識庫的時候了。最後，在專業領域中，並沒有一套標準的資料集或成功基準（benchmark）。所以，當你在設計改善流程的同時，其實也在定義「更好」這件事本身是什麼。

**John Liu：** 而在你進入循環其他部分之前，就必須把基準測試與評估設計成第一等級的設計元件，因為它會影響整個循環怎麼運作。時間有限，就先分享到這裡。如果想了解更多，歡迎參考我們的部落格，看看我們的 GitHub。非常感謝各位的時間。
