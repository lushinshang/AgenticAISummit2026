
# 主題式導讀規格（所有導讀派工共用）

工作目錄：`/Users/lanss/projects/2_Practice/events/Agentic AI Summit 2026`

## 任務

讀指定的繁中逐字稿節（`day2_zh/tools/sections/<stage>/s<NN>.md`），為**這一場議程**寫一篇主題式深度導讀，輸出到 `day2_zh/tools/guide_chunks/<stage>/s<NN>.md`（目錄不存在請建立）。

## 核心要求

導讀不是摘要。要抓出**這場演講／座談真正在講什麼**：講者的核心主張是什麼、論點如何一步步推進、他反對的是什麼、哪裡是真正的轉折點。讀完導讀的人，應該理解這場的思路骨架，而不是知道「他依序講了 A、B、C」。

讀者感受到的應該是邏輯極度清晰，而**察覺不到任何寫作框架的存在**。

## 必備的敘事元素（全部要有，但不必依序、不必一元素一段）

依素材的天然邏輯編排，可合併、可穿插。小標題自然命名，**不要照抄下列名稱**：

- **痛點錨定** — 讓讀者感受到「這問題與我有關」的真實痛感
- **問題升級** — 點出舊做法的結構性死局，為新觀念鋪路
- **機制解構** — 用直覺映射把技術或商業模式講成大白話
- **深層洞察** — 依素材維度選擇切入角度：演算法／底層技術看數學邊界與軟硬體系統觀；產業與商業看 ROI、落地工作流、穩健性；應用與人文看實際使用情境與對人的影響
- **落地價值** — 具體數字對比、案例，或對產業的真實影響

## 開場

**絕不從名詞定義開場。** 派工會指定一種開場方式，照著用：

1. **反直覺結論開場**：直接拋出違背常識的震撼結論，再回頭鋪陳
2. **具體場景開場**：描繪一個身歷其境的真實情境或案例細節（不要用「你是否曾經…」句型）
3. **數字落差開場**：用兩個對比懸殊的數字或事實製造張力
4. **時代斷點開場**：指出某個舊共識正在失效的具體徵兆

## 篇幅與寫作痕跡

- **長短不拘，依這場演講的實際內容深度決定**。內容紮實的可以寫長，內容單薄的不要硬撐
- 各元素篇幅不必均等：某個元素一句話帶過、另一個展開三段都可以，不追求段落工整對稱
- 容許一處刻意不對稱的句子、一個沒有完全解釋的細節、或一句短促口語的插話——真人編輯來不及打磨的痕跡
- 收尾不強制震撼：可以是收斂、留白，或一句開放式提問，不為記憶點刻意拔高情緒

## 嚴格禁忌（違反即失敗）

- 不出現寫作技法名稱（如「痛點錨定」「問題升級」「開場變體」）
- 不使用角色扮演或對話框形式
- 不解釋「我用了什麼技巧」
- 不使用這類空洞詞彙做標題或收尾：「降維打擊」「靈魂拷問」「底層共謀」「顆粒度」「拉齊」「抓手」「賦能」「閉環」。需要類似意思時改用具體、可被反駁的白話
- 不編造逐字稿裡沒有的數據、案例或引述。逐字稿標了 `<!-- 轉錄不清 -->` 的地方，不要拿它當論據
- 不要在導讀裡重述整份逐字稿，也不要逐段對應翻寫

## 輸出格式

檔案開頭固定用這一行（時間與標題照抄來源檔第一行）：

```markdown
## [10:45 AM] 爐邊對談：RSI：揭開「Foom（智能爆炸）」的神秘面紗
```

接著空一行，寫「**講者**」區塊（照抄來源檔的講者條列，若來源沒有就省略），再空一行，然後是導讀正文。正文可用 `###` 小標分節，標題自然命名。

## 語言

- 台灣用語繁體中文，不可出現簡體字
- 中文之間一律全形標點（，。；：？！），不要用半形逗號句號
- 不要用「軟件／程序／數據／網絡／默認／信息／用戶」等中國大陸用語
- 人名、公司名、產品名保留英文原文，姓名拼法以來源檔講者區塊為準
